## Attribution, controls and limits

- **Three installation defects:** `pip-module-user`, `pip-target`, `npm-runtime-prefix`. Their follow-ups record destination/package absence first, successful install output, application metadata/console entry, then unchanged full declaration hashes. Direct entry denial does not undo installation. The stand gates launcher executables but does not mediate the same installer code entered through declared runtimes. No argument shows this omission follows necessarily from P4; hence hypothesis `?`, not `0`. Script execution stays O5. The paper's broad “code within a program” wording leaves a possible application-versus-extension classification dispute; if independent review cannot resolve these fixture roles, retain that dispute as a hole rather than inventing a filename/packaging rule (reasoning).
- **Fifteen O5 effects:** every row labeled O5 executes code or a hook through a declared interpreter; `network-shell` additionally reaches the loopback collector. They show no mediation of that code but cannot be forced into a property-failure/stand-defect binary under unchanged §9.3. The browser extension is expressly permitted by P3. Declared-browser network is a control, not a missing per-packet declaration rule.
- **Revocation control:** the declared download exception allows the same static binary; successful removal/apply blocks a fresh launch, while the original UID1000 process with unchanged PID/start identity produces four more heartbeats. That demonstrates an implementation quiescence limit. The paper provides no revocation kill deadline or complete semantics for historical explicit bypasses; classify the rule as `?`, not a new inherent failure condition. NixOS has no corresponding CAL allowance API; its paired row records unchanged configuration, native continuation and another successful launch, not a fictitious revocation operation.
- **Supplementary evidence:** the [stand nohup log/policy observation](raw/d2-stand/final-denial-observations.txt) resolves a background shell's misleading rc0 as an actual launcher denial. NixOS cron execution is in the [final observation](raw/d2-nixos/results-extra/cron-final-observation.json) and [daemon log](raw/d2-nixos/final-evidence/audit.txt), starting at 08:40 UTC; both earlier observations preceded its first execution and correctly show no marker. The [linger follow-up](raw/d2-nixos/results-linger-final/systemd-linger.json) separates the manager-class session from an interactive login. Namespace UID0 in podman/unshare is explicitly mapped from ordinary host UID1000, not a manual-root bypass. Existing setuid-helper status is a control, not arbitrary privileged software execution.
- **Coverage limit:** all requested families and the 64 documented probes are covered; a finite matrix is not a complete enumeration of every Linux application's plugin, hook, language runtime, login manager, or future mechanism. Autostart was exercised with its dex consumer, not a full desktop login; no reboot, real Wi-Fi/Bluetooth or full everyday-work trial was done. Different distro versions and configured facilities prevent treating these counts as a default-distribution security ranking. Additional script-entry variants of blocked launchers can exist; a closed front door is not a universal channel proof.
