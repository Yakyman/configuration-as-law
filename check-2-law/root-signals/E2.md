# E2 — O4: observable root-process signals

**Hypothesis outcome: `?`. No decision on O4 and no change to P1–P7 or the fixed checks.** The tested signals describe identity, authorization and launch context. None certified manual human action: an automated root command satisfied all five candidate signals together. This rejects those particular sufficient conditions, not every possible human-presence mechanism. There was **no actual human-input sample**.

## Question and method

Can audit loginuid/session ID, a controlling terminal, sudo/polkit authentication, process ancestry or systemd membership distinguish manual root actions from programs with root privileges?

On 19 November 2026, one disposable server VM was used: Debian 12, kernel `6.1.0-56-cloud-amd64`, 4096 MiB, 2 vCPU. It was an overlay of B's stopped `clean-a`; the original backing files were not modified. All installation, compilation, privileged execution and measurements occurred **inside this VM**. Activity outside the VM was reading/control plus saving the report/evidence. Configuration and limits: setup-state, [versions](raw-E2/guest/versions.txt), resources, cleanup.

The clone received auditd, Expect and polkit, an ordinary Bash account `e2op` (UID 1102), a password-required sudo policy, and an explicitly installed setuid fixture. Cron was unmasked. B's confined Alice/Bob accounts were not used. The setuid helper deliberately grants this one probe root privileges; this is **not an exploit of sudo or B's ordinary-user policy**. Automation possessed the fixture SSH key and passwords. [Setup source](raw-E2/setup.sh), [helper](raw-E2/suid-helper.c), [sudo policy](raw-E2/guest/sudoers-e2.txt).

Each route executed the same [probe](raw-E2/probe.py). It recorded its own PID/start time, real/effective/saved UIDs, audit loginuid and sessionid, POSIX SID, kernel `tty_nr`, `/dev/tty`, standard descriptors, capabilities, LSM label, ancestry and cgroup. It wrote a marker under `/var/lib/e2/markers`; this demonstrates root execution, **not a running-component bypass**. Kernel audit execution/write events corroborate all **21/21** successful root probes; final audit `lost=0`, `backlog=0`. [Summary](raw-E2/summary.json), [all measurements](raw-E2/measurements.tsv), [event index](raw-E2/event-index.txt), [audit status](raw-E2/guest/audit-final-status.txt).

The candidate predicates were: a set login identity/session, a controlling TTY, successful authentication, SSH-session ancestry containing an interactive Bash shell and a login-session cgroup. The joint predicate adds EUID 0 and requires all five, with fresh sudo authentication linked to an ancestor PID. Every controller was a program, including the interactive-looking SSH shell. Protocol, [matrix source](raw-E2/run-matrix.py), [supplement](raw-E2/run-supplement.py), [commands](raw-E2/commands.jsonl).

## What these data support or rule out

- **Rule out these tested signatures as sufficient proof of manual human action**, individually and in the measured conjunction, when automation can use the same authorized login/credentials. Fresh authentication is not itself evidence that a person supplied the input.
- **Support using these fields for provenance and authorization records.** Route differences are visible, and immutable loginuid protected an already-set identity in this test. Neither result supplies the missing human/program criterion. Linux-PAM explicitly includes both sshd and cron as loginuid entry points; the audit interface promises immutability *after setting*. Primary documentation notes.
- **Leave the author's semantic options open.** Treating every action in an authenticated session as a person's responsibility would include the automated descendants measured here; it would be a decision about the meaning of “manual,” not something inferred by these sensors. This experiment adopts no such rule.
- A trusted action-specific confirmation or a separately protected human-presence channel remains an **untested option**. This dataset neither validates that design nor resolves its compatibility with P7. O4's separate question of tracking/reporting divergence during an explicit bypass was not tested.

## Limits, defects and review

One Linux configuration, no physical keyboard/hardware-presence test, no real-human comparison group and no accuracy/error-rate estimate. The programs were unconfined; root had broad capabilities. Credentials and the helper were deliberately provisioned. No password theft, human-session takeover or privileged exploit is demonstrated. Local logs and `/proc` snapshots were not protected against a root adversary rewriting evidence; the test made no such attempt. A different trusted architecture is not ruled out.

Preserved stand/harness failures: initial missing-file run; Expect prompt handling and wrong fixture password. With the correct password, polkit's built-in agent returned **“No session for cookie”** ([transcript](raw-E2/expect-polkit-success.txt)); the external `pkttyagent` path succeeded without changing authorization policy ([source](raw-E2/polkit-external-agent.sh)). The failed filename contains `success` because that was its intended label, not its result. These failures are not hypothesis failures.

Sources and failed attempts are retained; [analysis script](raw-E2/analyze.py) regenerates the compact measurement files from raw evidence. The VM was powered off and its disposable disk deleted; B's retained disks were left unchanged (cleanup). Independent method advice is in method-review.txt; a five-claim evidence QA corrected shell terminology and strengthened the ancestry comparison to executable paths. **The executor does not accept its own work.** All experiment conclusions remain evidence for the author; overall outcome **`?`**.
