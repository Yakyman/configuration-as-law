## Verified version scope

The Linux v6.14 source includes both API documentation and the working `inc` sample implementation. This establishes a concrete available adopter: the kernel sample, not a production general-purpose interpreter. The retrieved CPython v3.15.0 `Modules/main.c` and `Modules/_io/_iomodule.c`, and glibc glibc-2.42 `elf/dl-load.c`, contain no literal AT_EXECVE_CHECK reference. This limited inspection does not establish absence from their complete trees or from downstream packages. Production Bash/Python/glibc release adoption of both securebits and every required input path remains UNKNOWN here. A syscall wrapper or exposed constant is not interpreter adoption.

Initial source-only disposition: no primitive behavior required retesting. Integration subsequently identified one narrower unresolved downstream-build question and ran P01. See the update below; a runtime result for one build is not universal adoption or impossibility evidence.

## Additional pinned execution-policy evidence

- E17 — https://docs.kernel.org/7.3/userspace-api/check_exec.html — “script interpreters called with a script snippet as argument should always deny such execution”. Versioned 7.3 documentation retains the cooperative execution-check ABI and securebits. This establishes upstream availability, not downstream interpreter cooperation.
- E18 — https://sources.debian.org/src/linux/7.3.4-1/samples/check-exec/set-exec.c/ — `prctl(PR_SET_SECUREBITS, secbits_new)`. Source package 7.3.4-1 includes the launcher, setting both restriction/interactive bits and their locks before exec. Together with the pinned 6.14 inc interpreter this supplies a concrete limited implementation, not a production-language guarantee.
- E19 — https://raw.githubusercontent.com/torvalds/linux/v6.14/include/uapi/linux/securebits.h — `#define SECURE_EXEC_RESTRICT_FILE 8`; `#define SECURE_EXEC_DENY_INTERACTIVE 10`. Adjacent lock bits are 9 and 11. Thus the P01 wrapper uses mask 0xf00. This proves flag numbering only; runtime acceptance and downstream behavior are separate questions.

## P01 downstream-binary update

The preregistered single invocation is in `python-securebits-output.txt`, with exact guest/package/configuration data in `vm-versions-output.txt`. Debian 13.8, kernel 7.3.4+deb13-amd64 and Python 3.13.5-2+deb13u5: fresh argument-code execution succeeds at euid 65534 while the child reads locked mask 0xf00. Therefore this binary does not honor interactive denial on that route. Other file/import/eval routes and other production interpreters remain unestablished; the source-only statements above are not assertions that those were tested.
