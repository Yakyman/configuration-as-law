# Installation, scheduling, and container channels

Recorded 2026-11-22 UTC. Scope: C1–C6 and C9 only. This is source research and a constructive design analysis, not a claim that an existing distribution passes. No probe was run: the facts below are answered by primary documentation; the remaining integration uncertainties require a complete implementation, outside this task. Source excerpts and URLs are in `raw/install-sources.md`.

## Requirements used in every row

R = S2.1-3 (running **or startable** code is in force), S2.2-9 (programs regardless of installation method), S2.3-4 (record all in-force required objects), S2.3-5 (realize every declaration line), S2.3-6 (no path past declaration), S2.3-7 (built-in changes through declaration), S2.4-4 (stop and prevent restart on removal). S3-6 explicitly includes system, language and application package managers. S3-9 requires determinate version and source for an unambiguous install line. Code, including package hooks, additionally invokes S2.2-10 and S2.2-13. Services additionally invoke S2.1-3 and S3-10. Containers additionally invoke S2.2-12; confinement alone is not an exemption for a separately running container process.

Exact core sentences: S2.3-4: “**P1. Completeness.** Everything that must be recorded under Section 2.2 and is in force on the computer is recorded.” S2.3-6: “**P4. Law.** The system provides no path for changing, past the declaration, anything that must be recorded.” S2.3-7: “The built-in tools, including those executed with superuser privileges, change it only through the declaration: an installer does not install a program past the declaration but adds it to the declaration.”

The constructive mechanism below is deliberately stronger than a wrapper. An activation broker has exclusive write/enable authority over code and service policy. All ordinary callers, including built-in tools called by a superuser, are denied direct mutation by enforcing mandatory policy. A verified, immutable active code tree and mandatory execute/map restrictions distinguish active code from writable content. Package and build backends work on inactive trees; execution of their own build/hook code must already be recorded or take place inside a recorded VM under S2.2-11. Every application that interprets writable material requires the separate C7/C8 controls: this table never treats `noexec` as interpreter enforcement. “CLOSABLE” in a native-file row asserts closure of that row, not closure of all cross-channel interpretation paths.

## M1–M5 for every row

M1 requirement: S3-3 identifies the last successful application, while S2.3-4–7 require that selected generation's object inventory and authorization to agree. A package manager's successful exit is not by itself the hypothesis's application report. The broker must wait for admission, effective settings, and process state to match the intended lines. For C6, systemd-run's default `Type=simple` success precedes exec; E16 explicitly warns of this. For C1–C5 and C9, package/image existence is not proof of startability or correct dependency closure.

M2 requirement: S3-5 covers immediate power loss and reboot. Immutable code images assist integrity but are not a durable declaration-selection protocol. The declaration, code contents, configuration projection, authorization selection and boot selection must become durably mutually consistent before reporting. A rollback to a previous code tree after a success report would violate P2. This condition applies to all 39 variants; integrity primitives alone do not prove it.

M3 requirement: S3-4 retains the previous declaration after failed application or no report in one hour. Downloads/builds cannot become executable just because staging succeeded. Stage work without altering active objects, cancel or isolate stalled workers, preserve the previous active policy, and resolve no-report crash recovery against the previous declaration. Do not confuse an rpm/dpkg database rollback with rollback of services/accounts/rules or running processes. The separate mechanics analysis must address the exact report/commit boundary; this research does not claim to solve it.

M4 requirement: S2.4-4 is stronger than uninstall or disable. Revoke launch/import authorization of every code object no longer covered, stop existing processes (including descendants and container tasks), remove activation edges, and verify effective rules. Retaining cache/store/layer bytes is permitted by S2.5-1 only when they cannot be restarted under the active declaration. Copies, open descriptors and already mapped code make process stopping essential. A generic signature from a trusted publisher proves provenance, not current-declaration membership; signatures surviving removal require separate generation membership controls.

M5 requirement: S2.3-5 with S3-9/10 requires a line-by-line effective-state comparison. C1: content digest, executable reachability and package-induced services/accounts/rules. C2: interpreter, all dependency/import artifacts and environment selection. C3: image/app/runtime content, effective sandbox/host permissions and launchability. C4: imported exact bytes and controlled startability. C5: admitted build inputs when host-executed, compiled output digest, permissions and launchability. C6: effective unit/cron text, enabled/disabled state, timer/socket/dependency edges and process requirements. C9: image digests, all independently running programs, runtime configuration, mounts, ports and effective running/restart state. A package list alone cannot establish any of these checks.

## Mechanism findings and limits

- **Read-only images and stores:** E11 protects read-only blocks; E12 protects individual file content. Neither expresses current-declaration membership by itself. Retained previous store generations (E18) require explicit launch revocation. An immutable base still leaves writable data, service APIs, download-to-interpreter and container namespaces.
- **noexec:** E3/E14 close direct executable files and shebang execution from a covered mount. E14 documents interpreter bypass and specially patched shells. It does not prevent interpreting a readable file or guarantee coverage of user-created executable mounts.
- **IMA/EVM:** E21 permits appraisal at execution, executable mapping and file-read hooks. E22 protects security metadata. Measurement alone is not enforcement. Applying appraisal to every read would also reject new documents unless policy separates document-processing domains from code-loading domains. Appraisal accepts signed content rather than a particular active declaration unless keys/policy/object membership are tied to it. Not selected as a mandatory extra layer when immutable code trees plus mandatory policy already supply the needed invariant.
- **SELinux/AppArmor:** E10/E23 supply mandatory per-domain/profile access denial, including restricting a built-in privileged backend. Stock targeted or missing profiles are insufficient. Whole coverage includes user services, namespaces, mount authority, code mappings, API sockets, backend tools and policy loaders. Neither LSM infers that an arbitrary allowed read will be interpreted as code.
- **Landlock:** E24 restricts a process and descendants; it cannot constrain unrelated already-running processes or distinguish a data read from interpretation in the same allowed process. It is useful layered confinement, not a universal declaration engine or a substitute for a privileged activation policy.
- **seccomp:** E25 filters syscalls and numeric arguments, not arbitrary pointed-to contents or interpreter semantic steps. It can deny mount/namespace/memfd operations when those operations are unnecessary, but does not turn every code evaluation into an authorization event. Blanket JIT denial can break browsers; retain only carefully confined intended browser execution and separately analyze its textual exemption.
- **fapolicyd:** E7 offers trusted executable/library/script file policy with integrity checking. Trust database derived from package installation is not automatically a declaration. Filtering, ignored mounts, MIME recognition, generic read permission, interpreter streams and daemon failure behavior prevent treating default policy as universal proof. Trust enrollment and removal must follow declaration selection, not uncontrolled manager hooks.
- **Closed systems:** E14 demonstrates a shipped combination of noexec, modified shells, omitted interpreters and restricted pipeline utilities. This supports feasibility of selected closures, not unrestricted host programming. E26 supplies kernel sandboxing that also applies to native apps; it does not exempt independently running apps/containers under S2.2-12 or inventory their dynamic code. Closed-platform precedents are neither proof of the whole hypothesis nor a substitute for its stricter Removal condition.
- **Hooks/wrappers:** E2 exposes configuration override; E1 has lower-level direct management; E5/E6 show build/lifecycle execution paths. A wrapper with a post-install “record it” hook leaves a P4 bypass. The only sound use here is a user interface in front of mandatory write/execute/manager-API restrictions.

## Ordinary work and programming implications

These seven channels do not require losing any of the six ordinary actions. Installing and updating need base-generation/source/hash lines plus package/runtime/dependency lines and a built-in import/apply broker. Browser use needs a recorded browser and its executable dependencies; downloaded documents stay data while downloaded programs need import. Document editing needs a recorded editor and its dependencies; document macros, plugins and editor-language configuration invoke C7/C8 instead of becoming data by filename. Wi-Fi and Bluetooth require declaration-aware built-in management tools, handled in the ordinary-work analysis; denying their management APIs globally would be unacceptable, while brokering them is consistent with the channel design.

Programming can remain possible with writing scripts as content followed by explicit digest/version admission and a recorded interpreter, and with broker-managed pip/npm environments containing every executed dependency/build backend. A build VM offers another route under S2.2-11, with host launch of outputs still gated. Unrestricted execution of new host scripts without declaring them conflicts directly with P1/P4 when those scripts fall under S2.2-10; that conflict forbids that workflow, not programming as an ordinary action. Because Section 4.3 does not list programming as mandatory ordinary work, removing programming entirely would not by itself violate its six-action condition, but it is unnecessary for these bounded channels.

## Exact baseline and unresolved integration

Primary release information E27 gives Debian 13.8, released 2026-11-21; E28 pins the amd64 metapackage to 6.12.117-1 and `linux-image-6.12.117+deb13-amd64`. This is a real current baseline for old established facilities (noexec, dm-verity, SELinux/AppArmor, namespaces, seccomp), not evidence that every facility is enabled in the binary package or that a correct mandatory policy already exists. E29 lists Debian's series as Linux 6.12. Exact kernel configuration must be captured before any probe. The newer AT_EXECVE_CHECK/securebits route must be pinned independently and must not be claimed for this 6.12 baseline.

The unresolved question is whether a chosen full set of applications and brokers implements complete mediation and crash reporting correctly. A one-shot native-file denial probe cannot answer that. No testbed was built. No empirical result is fabricated. No NOT-CLOSABLE argument is asserted, because forbidding unrecorded launch while retaining mediated launch is a counterexample to the claim that these installation channels are intrinsically impossible to close.
