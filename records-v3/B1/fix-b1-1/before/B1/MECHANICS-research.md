# Application mechanics, privileged built-in tools, and Q2

Research record: 2026-11-22 UTC. Sources precede conclusions. No experiment was run: the documented primitive behavior below is already known; report semantics and algorithm interpretation cannot be settled by a probe. This is supporting research, not acceptance of a built testbed. No universal NOT-CLOSABLE result is established here.

## Primary evidence

Each quoted excerpt is deliberately short. Versioned documentation is preferred where available. These sources establish primitives, not the correctness of a complete configuration transaction.

### M4 boundaries that matter

The removal requirement is not secure erasure. S2.5-1 leaves inert remains and program state to design; S2.4-4 forbids their remaining in force. A retired executable may remain as bytes if no permitted path can start it or interpret it with relevant rights. Retained boot generations must not expose a path that starts uncovered retired code in the current declared system; rollback itself is a design question, not an independent contradiction.

Tracking only process ancestry is insufficient when a program loads a removed library, receives a file descriptor, or copies code into another already-recorded interpreter. Tracking all execution identities/holders, or replacing the whole affected userspace generation, avoids that counterexample. The latter has a real usability cost but Section 4.3 does not require uninterrupted sessions. Kernel modules and device firmware are more difficult: reboot/reload or device reset may be required, and full device rollback is not established by these sources. They are not silently solved by a filesystem snapshot.

### C10.4 source and strongest objection

Primary source: https://www.gnu.org/software/emacs/manual/html_node/emacs/Package-Installation.html — “then downloads and installs it.” The same page documents the `M-x package-install` entry point and loading installed packages into the current editor session. That is documented installation functionality, not an incidental inference from Turing completeness. S3-6 identifies a program whose purpose includes changing recorded objects; S3-7 expressly excludes an editor. For an editor package containing same-rights code, S2.2-10 supplies the recording requirement.

Strongest objection: an editor remains general-purpose in editing mode but is a built-in installer when `package-install` runs. Answer: that can reconcile the case, but the text specifies a program, not an operation or mode, and gives no rule for switching classifications. The alternative explicit-exclusion reading is also available. S3-8 expressly provides a definition-counterexample route when documented purpose still does not decide. Record TEXT-OPEN and submit the sentence conflict; do not choose a reading. This is narrower and stronger than alleging every shell escape is ambiguous.

A root general-purpose shell directly changing a protected file is expressly breaking under S2.1-7/S3-7; it is a boundary control, not a C10 NOT-CLOSABLE variant. Privileged administrative tools that can disable the guard are still built-in mutation paths: their disabling actions must be mediated or denied. Saying “root can always do anything” is not a proof because the text excludes specified root violations and Linux separates administrative authorities (E12).

## Success report and recovery: design obligation, not an established textual hole

S3-3: “The declaration in force is the declaration of the last application that the system has reported as successful; that report completes the application.” S3-4 preserves the previous declaration if no report arrives within one hour. Neither sentence identifies the report medium or recipient.

Reading A: a durable success record made available by the system is the report. The record can identify the committed generation, and recovery can select that generation. Reading B: the report is an external observer's received terminal/network message. Persisting the new boot selection before delivery creates a crash window in which recovery sees a committed new generation but the observer received no report. Persisting it afterward creates a window where the observer has success but the old generation boots. A correct protocol must resolve that additional requirement, not assume it away. The text does not demand the second, stronger reporting interface. A system may document its reporting interface; medium choice alone need not be a textual hole. This concerns M1–M3 on the listed channels, and does not justify an extra probe.

Strongest objection to a universal impossibility claim: a durable file is a valid report and can be the recovery commitment itself; the specification does not demand a remote acknowledgment. Answer: this objection defeats the universal claim. Report-medium choice alone is not classified TEXT-OPEN here; full multi-resource transaction correctness remains UNKNOWN until a concrete protocol is supplied and checked.

## Q2: algorithmic declarations and Understanding

S2.4-1 says exactly: “If there was no breaking, what is in force on the computer can be read from the declaration alone, without inspecting the computer.” S2.5-3 says exactly: “Nor is the form of the declaration part of the definition: it may be a list or an algorithm that computes what is recorded.” The second sentence permits algorithmic form. It does not expressly permit unrecorded variable inputs or waive Understanding.

Conditional argument, not a proof against every algorithmic system:

1. Let the same declaration files contain `record every script in D`, and let their evaluation inspect D outside those files. Assume this means recording the concrete current scripts, not a fixed already-contained set.
2. Let two otherwise admissible computer states have different scripts in D. The files constituting the declaration are identical, but the computed recorded sets differ.
3. P1/P2 can individually hold if each system authorizes exactly its computed set. Yet a reader given only the declaration files cannot distinguish those sets: identical input provides no information about which external state exists.
4. Thus under this reading the concrete in-force set cannot be determined from the declaration alone, contrary to S2.4-1. The supposed consequence does not follow merely from allowing an external-state algorithm plus P1/P2/P4.

Strongest objection: reading the declaration tells the reader the rule, and “every script in D” is itself the complete description; no enumeration is promised. Another objection: D is included in the designated declaration files, so it is not external. Response: the second objection removes the constructed premise and is valid. The first exposes an unresolved meaning of “what is in force”: intensional rule versus concrete objects. On the concrete-object reading of S2.1-3 and S2.4-1, the conditional external-input example is incompatible with Understanding. It does not show all systems or all algorithmic declarations impossible: a conforming system can disallow this particular dependency on unrecorded variable input. Treat a proposed intensional-rule reading as a question for textual review, not an automatic permission supplied by S2.5-3. A pure algorithm over recorded inputs, or a manifest whose expansion is included among the designated declaration files, has no such information deficit. That observation is a compatibility condition, not a proposed repair to the fixed text.

Do not claim undecidability makes every system impossible. A system can accept finite typed declarations, fixed defaults and terminating expansion algorithms. Nothing requires arbitrary programs as declaration algorithms or successful application of contradictory lines. S3-4 expressly recognizes failed applications. Whether a particular application has failed safely is the M3 obligation.

## Design implications and versions

The minimal evidenced mechanics are: inactive generation staging; durable files plus durable selector/parent-directory updates; an agreed report interpretation with deterministic boot recovery; removal of all old execution authorities followed by termination/restart of all holders; and independent comparison of actual state against finite typed declared values. C10 also needs mutation-sink mediation rather than shell wrappers.

Linux 6.12 versioned documentation establishes cgroup.kill support. systemd 257 documents suitable control-group stopping and has preexisting support since 187. Debian 13 release notes establish kernel 6.12-series/systemd 257 availability. These exact major/minor versions support the cited primitives; the release notes do not establish the exact current distribution point release, kernel package patch version, or configured LSM. Those must remain unclaimed here and be pinned by the builder. OSTree is supporting design evidence, not a selected verified testbed release.

No composed mechanism cited here proves all of M1–M5 for all channels. In particular, live network/account/rule changes and device effects must not be represented as solved by a read-only tree. No ordinary action is definitionally impossible from these mechanics alone; installation/update may interrupt a session, networking must go through a transactional built-in, and existing arbitrary hooks may be rejected. Those are compatibility costs to report, not universal failure proofs.
