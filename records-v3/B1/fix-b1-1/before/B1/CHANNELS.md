### Fixed requirements

### Why no universal impossibility result follows from ordinary bypasses

1. S2.3-6 forbids unrecorded change paths. It does not require every stock program option, arbitrary REPL, plugin, compiler feature, or administrative command to remain available.
2. Section 4.3 requires six ordinary actions and a declared positive example for each listed channel. It does not require those actions to use an unrestricted shell or a particular programmable editor. It does require retaining a controlled interpreter example: deleting C7 altogether is not a satisfactory positive testbed.
3. Mandatory execution/read restrictions and a cooperating evaluator can block a particular unrecorded input while retaining a declared input. The Linux 6.14 `samples/check-exec/inc.c` is a concrete limited-language example, not a conjecture that setting securebits fixes Python.
4. Therefore a bypass in an unrestricted interpreter, a mutable image system, or a wrapper-only package manager proves that configuration inadequate. It does not prove every Linux system must fail the same case.
5. No row supplies the Section 4.1 premise needed to turn that engineering failure into a universal 0. The complete existence claim remains ? pending the unknown integrations and textual review.

**Strongest objection:** the restrictions might make ordinary work impossible, or defeat the required positive program in a channel. **Answer:** that is a real design constraint, not dismissed here. Q3 retains concrete classes of tools for the six actions, and the design retains controlled code execution in every listed channel. Their actual composition and adapter use have not been demonstrated. Consequently this is not a whole-system 1 either. Removing all code interpreters is not the chosen existence argument.

There is likewise no justified “only by removal” claim. Disabling a feature, restricting a domain, rewriting an evaluator, or replacing a tool is not a proof that the entire class of programs must disappear. Where a full retained evaluator has no established control, the table says UNKNOWN.

### What each mechanic requires, in the prescribed order

**M1 — successful application.** S3-3 makes the success report the completion point. The report must identify the declaration whose objects and effective policy already satisfy P1/P2/P4, including generated services, dependencies and rules. Serialize conflicting applications; do not publish success while helpers can still change required state. Package-manager exit status, successful download, and a transient service job accepted by its manager are insufficient. Existing staging and comparison primitives support M1.01; a complete protocol across all resources remains M1.02 UNKNOWN. [Evidence: M1–4, I16.]

**M2 — immediate power cut.** For add, change and removal, boot must recover the exact reported declaration. File content, directory entries, policy, boot selection and their linkage to the report need durable ordering; a rename alone is not durability. OSTree's documented old-or-new guarantee is weaker than S3-5 once success has been reported. A durable success record may serve as a commit record; the text does not require an acknowledged remote message, so report-medium choice alone is not a textual hole. Runtime services and adapter state must be reconstructed and compared, not presumed correct because the image boots. This is the difference between M2.01 and M2.02. [Evidence: M1–4, O1–3.]

**M3 — failure or one hour without a report.** S3-4 keeps the old declaration in force. Inert preparation can fail without affecting it. Failure after service, rule, account, interpreter-policy or device mutation requires recovery of those effects; a package database rollback is insufficient. A timeout needs an effective watchdog/recovery path, not merely a log saying failure. The old code must remain startable as required, and candidate code cannot leak into active execution. The precise live rollback remains M3.02 UNKNOWN; no primitive probe can establish a protocol that has not been designed. [Evidence: M3–4; mechanics research.]

**M4 — removal.** S2.4-4 requires both absence of running uncovered contributions and impossibility of restarting them. Revoke access before permitting new requests, remove all activators, kill all code holders and wait for exit. A cgroup catches descendants only if migration and outside holders were prevented; loaded libraries, received FDs and injected/copied code can outlive their source process. Restart all affected sessions or reboot the userspace generation if needed. Reboot alone does not revoke old image copies or restore a rule correctly: the new generation must deny them. Inert remnants and retained generations are design choices under S2.5-1, not holes. An old valid signature cannot stand in for membership in the current declaration. Shared contributions stay only under the explicit remaining-lines exception. [Evidence: M5–8; I18.]

**M5 — every line.** Read actual content, permissions, effective rules and required lifecycle state. Resolve documented defaults as part of the comparison. A program need not be running unless its line says so (S2.1-4); it must have the permitted startability the line requires. Compare the declaration against actual state for P2 and separately look for extra required objects for P1. A lockfile/package database alone does neither. Finite typed lines admit concrete validators; unrestricted semantic assertions do not have a proved general validator here. [Evidence: M9–11; I15,I20; S3-9,10.]

## TEXT-OPEN cards

### T1 — Regenerable executable bytecode or JIT cache (C7.18)

**What the text lacks:** a priority rule for an object that is both a genuine cache and code executed with the program's rights. S2.2-5 says exactly “cache: after it is removed, the computer does the same, only more slowly;”. S2.2-10 requires same-rights code recorded. Choose a regenerated bytecode cache whose source remains available, so removing the cache changes only speed; a sole executable with missing source does not meet this card's premise.

**Reading A:** the cache exemption controls. The system can regenerate and execute this cache without recording a distinct code object, while source/interpreter remain recorded. **Reading B:** the explicit code consequence controls. The generated code must itself be covered before it can execute; deleting its line must revoke any uncovered execution. Whether a source line already covers derived code must be explicit enough to assess P2/Removal; do not assume it.

**Strongest objection:** the later explicit code rule settles priority. **Answer:** the text calls it a consequence of a rule that expressly exempted caches and gives no priority clause for their overlap. This is referred for textual review, not declared a universal system impossibility. Recording the cache or suppressing it can make a conservative implementation, but cannot decide what the text requires.

### T2 — Browser extension with browser-equivalent execution rights (C8.07)

**What the text lacks:** whether the named extension example is categorically exempt or only exempt while its effects and authority stay inside the program, and how that condition interacts with executable-code classification. S2.2-7 says exactly “settings that are in force only inside one program, for example the home page, theme, and extensions of a web browser.” S2.2-10/13 cover executed code. The concrete capability source is a privileged Firefox WebExtensions Experiment containing an API implementation: O10 documents full chrome privileges and packaging inside an extension. Its ordinary extension-page caller is not the same code object. This card remains conditional on the locally acting privileged implementation; it does not claim all modern extensions have those rights.

**Reading A:** the extension example remains an internal setting. Unrecorded extension execution is allowed. **Reading B:** only genuinely local values/interface-confined extensions qualify; same-rights executable extensions are code and require recording. A native messaging helper running as its own process is required under either reading (S2.2-9/12).

**Strongest objection:** “only inside one program” plus S2.2-13 already excludes all same-rights extensions. **Answer:** that resolves cases with documented outside effects, but the text does not state whether the local-setting condition follows current effects, potential authority, or the named class. The unresolved variant is a locally acting extension with browser-equivalent code authority, not a known independent native helper. No system requirement is chosen here.

### T3 — Partial confinement and the program's “own interface” (C7.21)

**What the text lacks:** an operational boundary for a sandboxed in-process evaluator that has some host APIs, but cannot do everything its enclosing program can do. The two explicit poles in S2.2-10 and S2.2-11 are not a specification of that boundary. S2.2-1/2 supplies the broad removal rule, but deciding whether the exception defeats that rule still requires knowing what “own interface” means.

**Concrete object:** the documented invocation `wasmtime --dir . foo.wasm` grants a module access to a selected host directory, while WASI excludes ungranted files and raw syscalls (O12/O13). The module executes inside the runtime; it is not a separate container process and is not an expressly named browser extension. Its host-file access and limited authority are known from primary documentation, so the uncertainty is textual, not an unknown behavior under S3-2.

**Reading A:** a restricted exposed API is the program's interface, even if it mediates selected file/network operations. The code may be exempt; the executing program is recorded. **Reading B:** host effects beyond an internal interface defeat the exemption; the broad removal rule requires recording this behavior-changing code despite its limited rights. Both readings require separately running helper programs recorded under S2.2-12.

**Strongest objection:** every API is an interface, so this simply permits all embedded code. **Answer:** that would also erase the own-rights interpreter examples in S2.2-10. The text supplies examples, not a measurable dividing rule for the intermediate case. A VM or a webpage expressly confined as stated is not itself this unresolved case.

A reviewed proposed fourth card, a root editor with an integrated package installer, is not counted: S3-7 explicitly classifies the stated editor route as general-purpose and its root changes as breaking. The original research objection and its rejection are retained in `REVIEW.md`; this synthesis controls the verdict. Unprivileged editor evaluation is still covered by C7/C8, and a separately invoked package manager is still C10.1.

These cards report classification questions, not revisions to the fixed text. If separate review determines the text truly cannot decide a covered object, Section 4.1 assigns 0 to that definitional case. This research does not convert an unresolved card or an engineering UNKNOWN into an accepted 0.

## Q1 — A recorded program can execute a data file with its own rights

**P1 can hold only if the file's code is also covered, or cannot become executable with those rights until it is covered. Recording the interpreter alone is insufficient.**

Premises: S2.2-10 expressly requires that code recorded; S2.2-13 classifies a file by execution rather than its “data” or “settings” label; S2.1-3 makes running or startable code in force; S2.3-4 requires every such object recorded. Suppose after a completed application an uncovered file can be evaluated by a recorded program with those rights, without breaking. It is required, is in force, and is not recorded: P1 fails. If an ordinary user can create/change that input past the declaration, S2.3-6 also fails. This is a definition-only **conditional failure argument**, not proof every system must permit the premise.

The strongest objection is that a declaration line recording the interpreter implicitly permits all its input. S2.2-10 explicitly requires the executed code recorded too; an actual line or algorithm that covers that input could meet the requirement, but merely naming the interpreter cannot be assumed to do so. Q2 treats state-dependent coverage. A writable directory, executable-bit check, suffix filter, read-only root or IMA exec-only appraisal does not solve the data-to-code transition. The kernel sees a read, not its semantic use. CPython's verified-open hook explicitly omits compile/exec/eval, and Python-level audit hooks are not a sandbox (T6–8).

Possible controls have different costs: immutable approved inputs plus read restrictions; a cooperative evaluator checking every file and refusing unrecorded snippets/streams; refusal of active document content; or genuine S2.2-11 confinement. Retaining an arbitrary interpreter's ordinary data access while permitting arbitrary eval/custom loaders is C7.08 UNKNOWN here. None of this makes a normal document code merely because it is readable: the relevant capability is execution as code with the specified rights.

## Q2 — An algorithm reads “every script in directory D” from computer state

S2.4-1 says exactly: “**Understanding.** If there was no breaking, what is in force on the computer can be read from the declaration alone, without inspecting the computer.” S2.5-3 says exactly: “Nor is the form of the declaration part of the definition: it may be a list or an algorithm that computes what is recorded.” The permitted **form** does not waive the properties or Understanding.

An algorithm can satisfy Understanding if the relevant result is determined by the designated declaration files and fixed documented semantics. For the proposed algorithm, distinguish D included among those files from D read as independent mutable machine state. In the latter case, if different contents of D change the concrete in-force code set, Understanding cannot hold on the concrete-object reading:

1. S2.1-1/2 identify the declaration as its designated files. Consider two separate applications/computers with identical declaration files and different external D, with no breaking in either; do not assume an in-place undeclared transition is permitted.
2. Let the algorithm obtain different script sets from external D in the two states. By premise its output, and the required/authorized concrete objects, differ.
3. A reader receiving only identical declaration files cannot determine which of the two sets is in force. Inspecting D would inspect the computer, the operation S2.4-1 says is unnecessary.
4. Therefore this particular dependence on unrecorded variable input is incompatible with Understanding. It is not an argument against all algorithmic declarations or all Linux systems, and S2.5-3 does not compel accepting that algorithm/input arrangement.

**Strongest objection:** the reader knows the rule “all scripts in D”, so knows what is in force symbolically. **Answer:** knowing a predicate over unavailable machine state does not identify the concrete objects described by S2.1-3 and required by P1. The text explicitly says “without inspecting the computer”; no sentence expressly waives this for algorithms. If “read” is instead intended to mean only learning such a predicate, that proposed alternative belongs to textual review, not an assumption used to certify P1 or Understanding. If D is itself among the designated declaration files, or its contents cannot affect the result, the two-state premise vanishes and the objection is valid.

Do not call algorithmic form itself a hole, and do not amend it to require one syntax. The compatibility condition follows from the other fixed requirement. Likewise no halting-problem argument proves every system impossible: a system need not accept arbitrary algorithms or contradictory/unbounded lines; failed application is explicitly contemplated by S3-4. M5.02 is UNKNOWN for unrestricted semantic validation, not NOT-CLOSABLE.
