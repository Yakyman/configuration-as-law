# Round 3 inventory implementation

`build/inventory.py` exposes `inventory(d=None, emit=True)` returning `(objects, summary)` and a standalone JSONL command. The recipe installs it behind the `stand-inventory` dispatcher in the main command. Exit 1 means uncovered candidates or mismatches; exit 2 means unresolved coverage. No exit status certifies complete P1. `complete` is always false: the census has unresolved semantic and namespace coverage.

Files are recursively enumerated from `/`, including container stores and writable trees; `/proc` and `/sys` receive selected runtime reads rather than recursive traversal. `/dev` is not recursively scanned, but `/dev/shm` is separately walked in full; other device-tree storage remains outside this file reader. Exact file content, owner, group, mode and symlink target must match an actual declaration line before file coverage is reported. Merely belonging to a package, directory, old generation or similarly named line does not cover an object. Non-signature files remain unknown rather than being silently classified as data. ELF/shebang signatures and known configuration locations identify uncovered candidates, not a semantic completeness proof. Services and timers are read from both installed-file and loaded-unit lists; available per-user buses are queried. Accounts, groups, ACL/capability xattrs, listening ports, nftables objects, saved networks, executable processes/mappings and accessible boot variables are separately reported.

Primary interface documentation checked before the planting test:

- [systemctl](https://www.freedesktop.org/software/systemd/man/latest/systemctl.html): “List units that systemd currently has in memory.” Installed unit files are separately enumerated; loaded-unit listing alone is insufficient.
- [proc_pid_maps](https://man7.org/linux/man-pages/man5/proc_pid_maps.5.html): “A file containing the currently mapped memory regions and their access permissions.” This is observation of mappings, not proof of their code semantics.
- [nmcli](https://networkmanager.dev/docs/api/latest/nmcli.html): “nmcli is a command-line tool for controlling NetworkManager and reporting network status.” The runtime listing supplements profile-file enumeration.

The fresh rebuilt-image planting test passes: this census surfaces every planted fixture without claiming coverage (raw evidence (not published: outside selected checks and direct evidence)). This answers the bounded integration question only. `build/round3-inventory-test.py` prints its expected result before direct-superuser planting in a disposable VM. It asserts reporting of program, unsuffixed code, container-tree code, service/timer/socket files, cron job, account, group, privilege file, login-key file, saved network, live port, live firewall rule, and boot configuration file. The unsuffixed code case must remain unknown, which is visible evidence of the semantic limitation. The boot fixture is a configuration file; the fixed external firmware selector cannot be changed or independently read by this guest. This helper does not test a real firmware-order change. The round-3 driver supplies fresh-VM and rebuilt-image evidence.

Open boundaries: arbitrary code hidden in input/data, alternate managers and detached namespaces, in-memory configuration/firmware and the semantics of unknown files are not completely classified. The fixed external boot order is not guest-readable. Full P1 therefore remains unproved. These are limitations of this implementation and its finite readers; no argument establishes impossibility for every system. Lists of dormant unit files and executable signatures can include objects not currently in force, so an uncovered candidate is not by itself a hypothesis verdict. Section 3's documentation/removal procedure is still needed for disputed cases. Filesystem scanning is a live observation, not an atomic snapshot; concurrent mutation may produce unknowns or inconsistencies.


## Additional bounded readers after review

The census now includes per-account effective `sudo -n -ll -U` output lines and fingerprints with supplementary group membership, process UID/GID/group/capability readback, polkit configuration locations, effective OpenSSH key-file locations, accessible kernel key IDs and permissions, Unix sockets and process `SSH_AUTH_SOCK` locations, scheduler configuration trees/at queue fingerprints, and mount metadata. Fingerprints of policy listings are evidence that a reader ran; they are not independent declaration coverage. Missing backends or failed reads produce explicit unknown entries. Key payloads, key descriptions, agent credentials, and arbitrary environment contents are not printed. Effective sudo listing lines are printed as policy evidence; the synthetic test guest contains no private command arguments.

OpenSSH `-T -C` is evaluated for each account in one explicit loopback connection context. `%h`, `%u`, `%U` and `%%` in configured paths are expanded; existing key files are compared against exact declaration file state. This covers per-user `Match User` settings in that context, but is not an exhaustive set of Match address, hostname or daemon-invocation configurations. Key-command configurations are hashed and remain unknown. These limitations are emitted per account.

- [OpenSSH sshd](https://man.openbsd.org/sshd.8) documents `-T`: “output the effective configuration to stdout and then exit.” Its `-C` connection parameters apply matching conditional configuration. This provides the bounded account/context reader, not an exhaustive context proof.
- [Linux proc_keys](https://man7.org/linux/man-pages/man5/proc_keys.5.html) identifies `/proc/keys` and `/proc/key-users` as “in-kernel key management”. Only visible IDs and metadata are enumerated; visibility is explicitly incomplete.
- [sudo manual](https://www.sudo.ws/docs/man/sudo.man/) is the primary reference for list mode. Automated retrieval was unavailable; this read-only invocation is not presented as a novel mechanism experiment.

Uncovered ELF/shebang file signatures now have `status=unknown` and explicitly say their in-force state is not established. A process executable readback separately establishes that its executable is running. The unsuffixed fixture tests visibility of unclassified bytes, not discovery that they execute. Effective privileges, keyrings, agent sockets, dormant scheduler configuration and mount entries remain unknown unless the actual finite line comparison establishes coverage. Full P1 remains `?`.


The file census explicitly traverses `/dev/shm` without traversing every device node. The planting helper includes a synthetic shebang file there and asserts its visibility without coverage. File-backed executable process mappings are now separately enumerated. Where permitted, `/proc/PID/map_files/RANGE` supplies the actual backing object for a full content/owner/mode comparison; `backing_lines` records exact backing-file matches only. The mapping itself remains unknown because backing-file bytes do not authenticate modified/private resident pages. Deleted and unreadable backing objects remain unknown; no pathname-only mapped-code coverage is claimed.

Remaining bounded-reader limits include: at queue output is fingerprinted/count-based rather than a per-job semantic declaration comparison; polkit configuration files are enumerated but effective decisions are not evaluated; SSH key paths cover the stated loopback Match context, not all contexts or dynamic key-command results; the login-key fixture proves a named candidate is visible, not effective authentication. The boot fixture is an inert configuration entry, not a firmware-order change. Device firmware beyond accessible Boot* variables and the external boot selector remain unresolved. These limitations keep M5.01 and M5.02 open.
