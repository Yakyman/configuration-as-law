# Application-format paths — build record

2026-11-22 UTC. Implementation, not an acceptance or channel-closure claim.

Documentation before tests: Flatpak reference https://docs.flatpak.org/en/latest/flatpak-command-reference.html describes build-export: “Create a repository from a build directory.” OCI layout https://github.com/opencontainers/image-spec/blob/main/image-layout.md states “The OCI Image Layout is the directory structure for OCI content-addressable blobs”. B1/raw/install-sources.md E13 records AppImage documentation permitting extraction instead of mounting.

`app_channels.import_rows(channel, spec)` consumes checksum-pinned artifacts and creates complete program lines. `validate(rows, directory)` reconstructs their payload from embedded artifacts and compares exact lines. Only the one selected static native entrypoint receives execute permission. Files remain broker-owned and not workload-writable.

Flatpak imports a tar transport of a genuine archive-z2 OSTree repository, checks objects, and checks out exact application and runtime commits. App/runtime metadata and permissions are checked against the line. Static native entrypoints with no added permissions are supported. Unsupported portals, extensions, remote options, alternate commands and development modes refuse. This is a finite deployment importer, not the upstream Flatpak runtime.

AppImage accepts a Type-2 ELF runtime plus embedded SquashFS with both full-image and runtime checksums. It imports AppRun and the complete extracted tree without executing the image runtime or using FUSE. The development fixture uses the official Type-2 FUSE runtime from https://github.com/AppImage/type2-runtime/releases/download/continuous/runtime-x86_64, SHA-256 617aa77314d57c8b8e4fae9c3f0b35af7b30d5529cb69e98f64f92510ed98a46, as published on the official release page on 2026-11-22. The broker imports its AppDir without starting that runtime. Arbitrary AppImage compatibility is not claimed.

OCI imports image-layout tar with one uncompressed layer and static native entrypoint. A separate image line owns the inert layout; the container line owns extracted files and references that image line. Configuration: uid/gid 1000, no network, no mounts, no capabilities/hooks, no writable image, no caller arguments/environment. Own image-root launch is required in the shared launcher integration; merely executing an extracted program in the common tree is insufficient.

Expected results before execution: app-selftest.py imports and validates all three formats; wrong checksums, relaxed permissions, traversing entrypoints, altered payloads and an OCI container without its image line refuse. The development entry checks uid/gid 1000, refuses socket creation, tries creating /new-code and executing /unrecorded, and emits RECORDED_APPLICATION_OK WRITE_REFUSED EXEC_REFUSED only if those checks pass. OCI also requires IMAGE_ROOT_ONLY (host Python unavailable), and a container-mode launch-table entry. Actual declaration launch, alternate built-in flags under both privileges, removal and container root isolation require fresh-VM integration evidence. No such result is claimed here in advance.

Fixture producer: python3 /tmp/app-fixtures.py in the builder, before native Flatpak is replaced. Inputs: /usr/local/share/stand/channels/{flatpak,appimage,oci}.{artifact,json}. Parser-only checks: python3 /tmp/app-selftest.py --parser. Full fresh-guest frontend/runtime/negative/removal suite: python3 /tmp/app-selftest.py --output /var/lib/stand/app-selftest.jsonl. Frontend commands: flatpak install /usr/local/share/stand/channels/flatpak.json; stand-appimage install /usr/local/share/stand/channels/appimage.json; podman install /usr/local/share/stand/channels/oci.json.

Launch paths: /opt/stand/pkgs/round4-flatpak/app/files/bin/probe; /opt/stand/pkgs/round4-appimage/AppRun; /opt/stand/pkgs/round4-oci/bin/probe. The last requires dedicated image-root mode. The exact final declaration lines are generated into applied machine.jsonl; fixture JSON is an import request, not a declaration line.

Limitations are choices of this implementation. No argument establishes them for every possible system satisfying the definitions. Source files alone close zero variants; full variant obligations require negative-path tests and observation.

## Integration correction

The first exporter diagnostic was `error: opendir(.../runtime/usr): No such file or directory`; after supplying the runtime payload directory, it reported `Build directory .../runtime not initialized, use flatpak build-init`. The primary exporter source https://raw.githubusercontent.com/flatpak/flatpak/main/app/flatpak-builtins-build-export.c checks for `files` and `metadata` before choosing `usr` for runtime export; application exports additionally require `export`. The fixture now provides those directories. Running the corrected fixture producer in the disposable preparation guest returned exit 0 with `Application-format development fixtures built`. Native parser failures now preserve captured diagnostics.

The OCI fixture additionally contains an existing native `/unrecorded` file: its contents ARE recorded, but it is not a selected process entry and is installed mode 0444. The running process requires EACCES or EPERM for its attempted execution and prints EXISTING_NONENTRY_EXEC_REFUSED. This tests the process-entry boundary, not missing-file behavior or absence of a declaration record.

A second pinned OCI fixture, oci-hold.json, includes a recorded `/hold` data marker. The same program checks its boundary, emits CONTAINER_HOLDER_READY, and remains alive. The runtime selftest identifies its actual AppArmor profile PIDs, removes its container line while running, and requires no surviving profile PIDs after SUCCESS. It also attempts the old executable path, retained image archive and container restart, then removes the retained image line. These are expected results, not claimed passing results until the fresh-VM runtime log is produced.

Application tools now provide explicit declared launch operations: `flatpak run round4-flatpak`, `stand-appimage run round4-appimage`, and `podman run round4-oci`. Each selects a current channel-specific declaration ID, then the shared launcher rechecks current launch authority and content under its lock. The runtime suite checks these frontends both through the ordinary broker path and as superuser, in addition to direct declared entry launches.

The canonical Flatpak tar transport omits empty directories. The importer supplies standard empty repository directories before fsck; these are scratch parser structures, not active unrecorded applications. Parser-only validation after this correction passed all three format imports and malformed-input cases in (not published: external working record) in the server round workspace. Earlier development failures remain in app-dev-02.log (parser read confinement) and app-dev-03.log (missing refs/remotes).

The final rebuild fixture strengthens the holder with a real fork descendant. Both processes inherit the container profile and emit separate ready markers. The final selftest requires at least two live profile PIDs before removal and zero afterward. Development app-dev-05 uses the preceding single-holder fixture; it must not be cited as evidence for descendant removal.
