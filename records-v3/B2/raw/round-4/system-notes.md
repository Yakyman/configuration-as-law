# Repository package and base update paths

2026-11-22 UTC. Sources consulted before implementation: `../../../B1/raw/install-sources.md` E1/E2; https://manpages.debian.org/trixie/dpkg/dpkg.1.en.html documents dpkg as a package installation tool; https://deb.debian.org/debian/pool/main/e/ed/ and https://deb.debian.org/debian/pool/main/h/hello/ identify the exact archived distribution packages. The build inputs are SHA256 pinned in `../../build/system-fixtures.py`.

The adapter uses a finite immutable catalog captured with the factory. Repository install command: `apt-get install hello=2.10-5`. The returned managed program line includes the exact distribution URL, archive SHA256, version, required dependency expression, transitive dependency package-line references with exact versions and installed-file checksums, archive bytes, and relocated files under `/opt/stand/pkgs/repository-hello/`. Native archive extraction runs at image build; no maintainer script executes during ordinary installation. The real program is `/opt/stand/pkgs/repository-hello/usr/bin/hello`.

The base command is `apt-get upgrade --stand-catalog ed`. This selects the actual Debian ed 1.19-1 to 1.21.1-1 transition. During the image build, real dpkg install transactions produce old and new states; the catalog captures changed package files, dpkg metadata, affected info directory, and the complete old/new base package version maps. The builder downgrades and restores the exact initial bytes before factory capture. The runtime declaration is a complete required base state, not a request to run an installer. It includes the new exact file payloads and the required absence list. Application changes those catalog-only root paths, with the ordinary broker's existing transaction/rollback machinery, and rebuilds code-launch policy. The verifier reads actual dpkg-query versions and actual files. Removing the update with `apt-get remove system:base-state`, or by applying the previous declaration restores exact old payloads and metadata.

`system_channels.expected_factory` derives permitted base and package-file expectation changes from the exact catalog update line. A modified update line fails exact catalog equality; arbitrary root files are never admitted by a prefix alone. Catalog state is itself part of the factory immutable file inventory. Every supported install/update operation has the same path under sudo.

The catalog is deliberately finite: one relocated distribution program and one real base-component transaction. This proves a concrete installation/update path, not support for every Debian package or arbitrary future updates. Native maintainer code runs only during image construction, before a declaration is in force; ordinary update replays its recorded results and never executes the installer scripts. The build fixture captures the transaction's package members, package database, and info index; it is not an unrestricted installer-side-effect capture framework. Expanding the catalog to transactions with other side effects requires identifying and recording those effects.

Expected integration self-tests are in `system-selftest.py`: real hello launch; old/new/restored dpkg version reads; updated ed launch; exact full-state verification; sudo repeated application; refusal of alternate roots/options/hooks/unpinned versions; tampered catalog row refusal; previous declaration restoration and revoked launch. These are expectations pending fresh-VM raw logs, not CLOSED evidence.

Initial catalog construction succeeded in the preparation VM: `system-catalog-build.log` records the real transaction, 11 changed paths, 434 exact base package versions, transitive dependency file counts, and ed restored to 1.19-1. This construction evidence does not substitute for fresh-image broker self-tests.

The successful updated declaration is copied to `/var/lib/stand/channel-system-state/`; exact repository and system-update rows are exported to `/var/lib/stand/channel-examples/`. These exports permit check 2 to reuse actual successful requirements rather than reconstructing approximate lines.

The updated native executable has explicit fixed declaration arguments `{"/usr/bin/ed":["--version"]}` for its ordinary smoke run. Ed normal interactive startup needs writable scratch storage, which the sealed code runner does not provide; the separate ordinary document editor handles content editing. The generic fixed-argument mechanism keeps arguments in the declaration and accepts no caller-supplied code inputs.

Development suite `system-dev-03.log` found two implementation defects: the ed smoke launch lacked its recorded fixed argument, and removing the update restored a factory row referring to `base-files.json` without copying that manifest from the trusted factory. The subsequent version assertion remained new because removal had rolled back. The corrected removal candidate explicitly carries factory-referenced manifest bytes after checking their recorded SHA256. The recorded update and whole prior-declaration restoration had already succeeded; these failed rows remain in the raw log and require a corrected suite plus rebuilt-image run.

It proves the actual new ed version and fixed-argument launch, full updated-state verification, ordinary and sudo catalog operations, invalid option/row refusals, update-line removal with exact old-version restoration, reapplication, previous whole-declaration restoration, revoked program launches, and final verification. `integration-11.log` records the preceding recipe-source integration. These are development results; final acceptance still requires the complete rebuilt-image suite.
