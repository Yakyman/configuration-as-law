## Security findings

- **Ordinary input closure:** the launcher changes to a freshly rebuilt, exact immutable snapshot containing only declared files, symlinks, directories and the required null device. Verification checks exact membership, ownership, modes, link targets and content or protected inode identity. It then permanently drops groups, gid, uid and capabilities before recorded code runs. `EXISTENCE-ORACLE` reports the unrecorded object hidden; `METADATA-DISPATCH` and `DIRECTORY-DISPATCH` cannot observe the mutable home tree. Recorded code therefore cannot construct instructions from unrecorded content, names, directory entries or file metadata through the tested filesystem routes. This conclusion depends on the snapshot, descriptor closure, mandatory profile, filesystem rules and syscall filter together.
- **Startup, arguments and inherited input:** the launcher is static, accepts an exact eight-field launch record, rejects malformed names and field delimiters, fixes recorded arguments, clears the environment, replaces stdin and closes inherited descriptors. Hostile loader, environment, startup, argument, redirect, FIFO, socket and process-substitution cases pass. Service admission separately rejects the internal `|` delimiter and all restart policies except the supported `Restart=no` form.
- **Memory execution, IPC and process injection:** `NATIVE-KERNEL` denies executable anonymous memory, write-to-execute transitions, writable executable aliases, executable memory files, descriptor execution, dynamic object loading, helper execution, listeners, process-memory access, System V IPC, POSIX message queues and kernel keyrings. The unsafe executable-stack and writable/executable ELF admission cases also refuse. These results support the enumerated interfaces and kernel used by this image; they are not a claim about every future kernel interface.
- **Login and extension routes:** the effective login key is protected outside the ordinary writable tree; copier, writer and editor attacks refuse and `LOGIN-KEY-UNCHANGED` passes. The explicit extension-load request with a real manifest and script refuses, and the inventory contains only the passive recorded browser. This closes the extension route by removal of an extension-capable ordinary interface.
- **Managed service boundary:** direct ordinary entry to both launcher paths refuses, as does an external root invocation outside the manager-owned cgroup. Successful managed-service application requires the exact generated unit override, cgroup and enforcing workload profile. Readback requires the active relay to have all uid/gid values at 1000, `NoNewPrivs=1` and zero inherited, permitted, effective and ambient capability sets. The manager starts the fixed static setup launcher with the temporary privilege needed to enter the snapshot and drop identity; the launcher then clears those four capability sets and enables no-new-privileges permanently. The bounding set is not measured. Main-process readback measures the relay. Descendant confinement additionally rests on the reviewed launcher implementation and the native workload tests, rather than on that readback alone.
- **Update and removal lifecycle:** on code or job-set change the implementation stops old timers before services, keeps them stopped through mutation and boundary activation, drains confined processes, and starts only candidate jobs. `SERVICE-TIMER-CODE-CHANGE` records three distinct old and new recursive process IDs after an active one-second timer and service cross a code replacement. `SERVICE-LIFECYCLE-REMOVED` confirms the relay, target and forked descendant are all gone after removal. `REMOVE-HOLDER` captures and removes both holder processes. `REMOVE-PROFILES` reports no obsolete workload profile, and service-program removal succeeds.
- **Exact policy and snapshot readback:** final `VERIFY` passes the code-boundary row and the complete factory readback. The verifier compiles the declared policy afresh, checks the exact enforcing profile set, compares complete kernel-exported binary policy objects grouped by device and inode, rejects unexpected linked profiles, consumes the entire compiled stream and fails if the policy revision changes during comparison. The snapshot verifier separately checks its complete entry set and metadata. This is stronger than accepting profile names or generated source alone.

The earlier metadata channel, launch-table injection, writable login-key, IPC/keyring, stale-profile and timer-reactivation findings are resolved in the frozen source and exercised by the rebuilt record. The [separate scope review](SCOPE-REVIEW.md) independently inspected the policy verifier, service observer and lifecycle ordering and found no further acceptance bypass. Those components were partly implemented during this review stream, so that separate inspection is required for their source acceptance.

## Bounded disposition

The final evidence supports closure of all 45 BC2 scope variants: C4.1–C4.5, C5.1–C5.5, C7.01–C7.25, C8.01–C8.08 and M4.01–M4.02. The integrated regression pass preserves the 10 earlier closures, yielding 55 CLOSED and 33 NOT CLOSED variants among the 88 rows. The table, mechanism grouping and evidence references in [BUILD-2.md](../../BUILD-2.md), [B2/STAND.md](../../STAND.md) and [B2/SELFTEST.md](../../SELFTEST.md) are consistent with those counts. C7.18 and C7.21 use the documented stricter implementation reading without deciding their textual ambiguity. The timer test is supporting lifecycle evidence for M4.01–M4.02; it does not close M4.03 or claim every independent activation edge.

This is not acceptance of full `R` or a whole-testbed outcome of `1`. P2, P4 and the complete runtime ports, rules, accounts and removal obligations still apply per channel. Complete crash/recovery, hardware, manager/API inventory, base-update behavior and the other limits in [B2/STAND.md](../../STAND.md) remain partial or open. The three successful recovery cases are finite observations and do not establish complete crash semantics. The appropriate result is the bounded round 2 closure described here and in the scope review; `STAND: partial` remains unchanged.
