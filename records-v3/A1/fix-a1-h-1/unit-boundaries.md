## Findings 1 and 2

The previous extent gave 598 unit-related rows a confirmed single-program premise without establishing it: 486 system-unit rows, 36 user-unit rows, and 76 stored unit outputs. The corrected per-row check is `unit-file-reader-check.tsv`. It preserves the exact original evidence and records matching saved unit-file/path inventory lines for each ID, restricted to the same manager scope. Identical names in system and user managers are not interchangeable. Independent verification caught three cross-scope matches in the first new draft; those were removed before finalization. The inventory stores names, fragment paths and states, not a complete captured body plus applying-program trace for each of these files. For 21 inventory-unit rows, the actual unit-file state is disabled (not merely the preset column): the manual defines this as containing installation instructions, establishing systemctl as an applier under the hypothetical file reading. Those file readings are explicitly EXCLUDED-MULTIPLE-READERS in the per-row checks. The other 577 rows lack evidence establishing presence or absence of a second applier. A path is not evidence of its section contents. An enabled link may have been created manually; static status establishes no enablement provisions, not the absence of every other applier. Therefore none of these 598 rows is retained as a confirmed H1 example on that evidence.

The review's generic warning about systemctl is valid. Pinned upstream documentation is saved as `raw/systemctl-v260.xml` (lines 897–924 and 1106–1112) and `raw/systemd.unit-v260.xml` (lines 2241–2246); URLs and source hashes are in `raw/systemd-sources.json`. The systemctl enable description says: “This will create a set of symlinks, as encoded in the [Install] sections of the indicated unit files.” The unit manual says: “Unit files may include an [Install] section”. The second quotation matters: the first does not establish that every exact file has applicable installation values. The saved NixOS generator `(not published: adjudication scratch):740` also generates this section conditionally. No actual inventory object is silently replaced by a file to assign EXCLUDED-MULTIPLE-READERS. The 21 conditional file exclusions combine exact saved disabled-state lines with the manual’s state definition at lines 1116–1117. The absence of an established second applier is not proof of a single applier either.

The 522 inventory-unit objects are separately marked **READING-DEPENDENT**, including the 21 whose hypothetical file reading is excluded on the second-applier evidence. Two readings remain on the record: the row denotes the managed service/mount/target with its state; or it denotes the settings in its backing fragment. The prior review silently selected the second. Section 4.2 inventories services/timers, and Sections 2.1 and 2.4 discuss a service's enabled/running state; neither makes an inventory unit identical to a file. A fragment may explain behaviour without changing the identity of the object. The text does not settle that substitution. It remains an unresolved H1 candidate, not a refutation, a factual ? under S3-2, or an independently counted new hole type. Author choice is not made here. `../QUESTIONS.md` records the two readings.

The 76 stored unit outputs are actual stored-file candidates, separately marked **FACTUAL-UNKNOWN** because the single-program premise is not established for their exact contents. The two unit-only aggregate rows `nixos-ee908f90c5` and `nixos-b9f001fe55` are also factual unknowns: their former constituent proof depended entirely on the affected unit files. No state exemption is newly asserted for these stored files.

## Finding 3 and aggregate propagation

The review is right to challenge the single-manager claim for `coreos-4d2a7c7537`. Its stronger statement that the quoted enable passage itself proves two programs apply the resulting links does not follow: the passage describes systemctl reading installation directives and creating links; the manager follows the resulting links. Source settings and their outputs are distinct objects. This is not evidence that link creation alone is a second application of a link's value. No rule equating creation with application is added.

The former proof of a unique applying program is nevertheless inadequate, so this row is **FACTUAL-UNKNOWN**, not confirmed, not automatically excluded. The same correction is propagated to six other /etc/systemd groups whose former confirmed rationale relies solely on enablement/unit members. Their exact IDs are in `changes.tsv`. Two groups retain independently established non-unit constituents: `nixos-b86fee9a16` (journald/logind settings and generator environment) and `arch-b86fee9a16` (80-dhcp.network). Those retained groups no longer claim enablement/unit constituents as confirmed. Linger rows, which did not rely on unit files or the challenged enablement-link argument, are unchanged.

Kinds: 42 system-closure-store-object, 40 stored, 31 package-owned-paths, 1 package. Unestablished candidates comprise 243 factual unknowns and 522 reading-dependent unit rows. The previous 35 exclusions are unchanged. The arithmetic is 721 − 598 − 2 − 7 = 114; factual unknowns are 158 + 76 + 2 + 7 = 243.
