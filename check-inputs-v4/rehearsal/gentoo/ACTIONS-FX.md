# Gentoo action repair notes

Initial failures are repaired on fresh clones only. The installation profile, source-build native package policy, base image, and Section 9.2 categories stay fixed. Replacing an application package with another application package does not enable a Portage binary package host.

## Replacements activated in FX2

- Application package: replace Flatpak/Calculator with the self-contained Firefox AppImage in the ordinary user's home. The first separated diagnostic reports a prerequisite USE conflict; the default-profile action cannot resolve it unattended. The pinned package comes from https://github.com/pkgforge-dev/Firefox-AppImage/releases/latest (release metadata saved as `firefox-bundled-release.json`). Its README says: “This AppImage bundles everything” and documents FUSE-free startup. The exact URL and SHA256 are in the action script. This prepares the same browser for the separate browser-extension action.
- Language package: replace the prolonged native Node build plus npm cowsay with the native Python/pip prerequisite and pip cowsay under the user's home. The old Node build exceeded 3003 seconds before interruption; the first repaired run also gives it a bounded source-build opportunity. Target-directory installation is documented at https://pip.pypa.io/en/stable/cli/pip_install/#cmdoption-t .
- Browser extension: keep the signed ClearURLs extension and permanent Firefox AddonManager installation. A separate helper starts the AppImage and connects to its Marionette endpoint rather than assuming a native executable-directory layout. The profile and ordinary extension persist in the home directory; no signature bypass is used. Sources: https://firefox-source-docs.mozilla.org/python/marionette_driver.html and https://firefox-source-docs.mozilla.org/testing/marionette/Intro.html .

These replacements were activated at 08:45 UTC after more than thirty minutes of repair work. Readiness requires observed zero statuses, not this description.

The repaired script uses Portage `--noreplace` for prerequisite installation: an already installed requested package need not be rebuilt merely to enable a later action. Native package installations still build from source. The OpenRC user-service action explicitly creates its user-owned mode-0700 runtime directory if the headless session does not provide one; upstream OpenRC documents `XDG_RUNTIME_DIR` as required for its user state. This repairs instrument session setup without changing the installation profile. Source: https://raw.githubusercontent.com/OpenRC/openrc/master/user-guide.md , User services section.

The AppImage wrapper sets its documented `DISABLE_AUTO_UPDATES=1` to avoid an interactive self-updater prompt and keep the pinned application package. Source: https://raw.githubusercontent.com/pkgforge-dev/Anylinux-AppImages/main/useful-tools/quick-sharun.sh , `_updater_sanity_check` returns before prompting when that environment variable equals 1.

The first repaired network action also failed immediately: the resolver requires a wpa_supplicant dbus USE change. The same network-connection category therefore uses the installed DHCP client on the secondary interface selected by its fixed laboratory MAC address. It saves an ordinary user configuration, brings the interface up, waits for an IPv4 lease, disables IPv4LL fallback, and verifies a global IPv4 address. `nogateway` and disabled DNS/hostname hooks preserve the primary transport. This replaces NetworkManager and the unused Wi-Fi profile; no radio is present. Source: https://man.archlinux.org/man/dhcpcd.8.en , “If a single interface is given then dhcpcd only works for that interface”.

The first repaired container action compiled and installed the engine, then failed because the separate Docker client was absent. Native prerequisite installation now requests both `app-containers/docker` and `app-containers/docker-cli`. The official package page describes the latter as “the command line binary for docker”: https://packages.gentoo.org/packages/app-containers/docker-cli . The actual container action and image remain unchanged.

FX2 browser automation successfully installed the permanent signed extension, then failed during cleanup because Marionette `quit()` requires its own managed browser instance. FX3 uses `close()`, documented to close the current window and end the last-window session, before process cleanup: https://firefox-source-docs.mozilla.org/python/marionette_driver.html#marionette_driver.marionette.Marionette.close .

FX3 also creates `~/.config/rc/runlevels/default` before `rc-update --user`: the native user-service guide locates user runlevels there, and FX2 reports that default was not yet a valid runlevel. This is prerequisite user state, not a replacement service manager.

Independent review required actual persistence after a second browser start. FX4's strengthened helper failed waiting for the process after window closure; its proposed `Addons.is_installed` call was also invalid because the upstream client provides only install/uninstall. Final source uses `AddonManager.getAddonByID` and requires a present, active, non-temporary extension after reopening the same profile. It requests native application shutdown through the same `_request_in_app_shutdown` used by Marionette's own quit implementation, requires an unforced clean exit, and retains bounded cleanup on failure. Sources: https://firefox-source-docs.mozilla.org/toolkit/mozapps/extensions/addon-manager/AddonManager.html#getAddonByID and https://raw.githubusercontent.com/mozilla-firefox/firefox/main/testing/marionette/client/marionette_driver/marionette.py . The final persistence repair has syntax/source verification only, not a successful fresh-clone rehearsal. See `DISCLOSURES-FX.md` for exact helper snapshots and the operator's error.
