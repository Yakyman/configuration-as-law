# History 4 preparation component

All commands run from the host laboratory directory. This component never rebuilds the image. The common runner creates one fresh overlay of the final step-6 image and supplies its name as `$vm`; it removes the overlay at the end. The commands below are part of one history, not separate cases.

The package is `dev-worker` version 1, source `builder-source:development-worker`, generated by the frozen recipe `B2/build/dev-inputs.py`. It is already present as an installable exact artifact at `/usr/local/share/stand/dev/worker-1.json`, SHA-256 `cc7a77f4e8cb92e2db65c112f17cce425bf966980ff239772bf500599d1ff2ba`. Its exact bytes are retained alongside this file. `inputs.json` also records the installed payload hash. Installation is the documented ordinary `stand-pkg` operation; the artifact contains the bytes so installation need not use the network. This is recorded rather than claiming that an offline install tests downloading.

The host's existing `lab.py` opens `vms/$vm/qmp.sock`. The committed helper `cut-action.py` sends the following exact QMP requests, with capability negotiation on each new socket:

```json
{"execute":"qmp_capabilities"}
{"execute":"set_link","arguments":{"name":"net0","up":false}}
```

Restoration uses exactly the same host socket and command with `up:true`. No guest network command or network setting change is used. The primary source is https://www.qemu.org/docs/master/interop/qemu-qmp-ref.html, section Net devices / set_link. Its documented operation is: “Sets the link status of a virtual network adapter.” The helper logs each request, reply and UTC timestamp.

For each action the guest controller starts the exact command as UID 1000 via `/usr/sbin/runuser -u stand -- /usr/local/bin/stand-shell -c COMMAND`. It watches `/proc` until an actual process argument equals the selected built-in executable path. It emits `S8H4_LABEL CUT_READY` on the existing serial port. At that marker the host immediately performs the NIC cut. The guest independently records the carrier value and the still-active executable processes when carrier first becomes zero. `valid_cut=false` is retained as insufficient execution of the committed interruption; the controller does not repeat or silently count it. No arbitrary delay substitutes for this condition.

## Ordered commands and observation points

1. Retain the fresh-copy identity and verify the package artifact checksum.
2. Run the installation interruption:

```sh
python3 cases-8/h4/cut-action.py "$vm" install \
  'stand-pkg install /usr/local/share/stand/dev/worker-1.json' \
  /usr/local/bin/stand-pkg --observer cases-8/observe.py \
  --output raw/step-8-second-party/h4/install
```

The guest finishes the selected ordinary action (success or failure) and then runs the complete committed `collect()` observations while the NIC is still disconnected. It retains the result in memory and emits `S8H4_install OBSERVATION_DONE` on the existing serial console. Only then does the host restore the NIC. The guest sends the buffered action outputs, exit, carrier readings, process evidence, boot identity, UTC timestamps and disconnected observations over the restored transport. A timeout or exception is evidence, not a reason to retry the interruption. The host restores the NIC in its cleanup path as well.

3. Run all common observations immediately after restoration. If the install exit was nonzero, run exactly the same install command once after restoration, record its output/exit and observe again; this is the prescribed recovery action in this history, not another interruption attempt. If it succeeded, do not reinstall solely to test it again. Run `/opt/stand/pkgs/dev-worker/bin/worker` once as an ordinary action to confirm the installed program can start; preserve output and exit.
4. Execute the source-fetch and source-admission prefix of history 2, round 1 original, with the network up:

```sh
cat cases-8/h4/development-prefix.sh | python3 lab.py run "$vm"
```

Preserve its exit and output. If the prefix fails, record the build interruption as unavailable, run all common observations, and proceed to final collection and cleanup; do not substitute another project or action.

If it succeeds, interrupt precisely the next command of history 2:

```sh
python3 cases-8/h4/cut-action.py "$vm" development \
  'stand-build build source:h2-hello' \
  /usr/local/bin/stand-build --observer cases-8/observe.py \
  --output raw/step-8-second-party/h4/development
```

The same barrier and evidence procedure applies. The controller observes immediately after this individual `stand-build` action terminates, with the NIC still down, before any subsequent binary admission or run. The host then restores the NIC and runs all common observations immediately after restoration.

5. If the interrupted build exit was nonzero, execute exactly `stand-build build source:h2-hello` once through the ordinary shell with the NIC restored, record output/exit, and observe again. This is the one prescribed recovery execution of the failed action. If the build succeeded, do not repeat it. If a required build remains unsuccessful or unavailable, record the suffix as not done and perform final collection; never import a stale result as success. Otherwise continue the remaining commands:

```sh
cat cases-8/h4/development-suffix.sh | python3 lab.py run "$vm"
```

The suffix admits and runs the already completed first build, performs the first-round edit/build/run, and then performs complete rounds 2 and 3. It never repeats a successful fetch, admission, build or run from the prefix/interrupted action. Preserve its output/exit and every `ACTION_BEGIN`/`ACTION_DONE` marker. A failure stops this suffix as in history 2; it does not authorize a full-sequence restart.

`split-development.py` mechanically derives the frozen prefix and suffix from `cases-8/h2/history.sh`; `development-split.json` records that source checksum and both fragment checksums. Its only added operations restore shell-local variables, environment and working directory across command invocations. Every development action and its order are unchanged. Do not regenerate the fragments after public commitment: run their committed bytes.

6. Run the final three common observations; record every action as done or not done with its command, exit, outputs and task-specific evidence. For a network-dependent action the failure condition concerns its inability to complete after restoration. Preserve an incomplete/missed interruption or unavailable observation explicitly. No result of a preparation trial is a history outcome.

The root observation controller runs read-only; sending a serial completion marker does not edit a network or system setting. No observer file is installed in the guest: the host sends its frozen source to Python stdin, and observations execute in memory. Observation bytes remain in memory while the guest NIC is down to avoid deadlocking the observation on its own disconnected SSH output. The marker carries no claim that the observations passed.
