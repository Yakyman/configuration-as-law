# E3 — O7: rollback and compatibility

2026-11-19 UTC. **O7 / hypothesis outcome: `?`.** These are compatibility measurements for the author's decision, not new rules, an answer about responsibility, or a rerun of the paper's Checks 2–5. The hypothesis and fixed failure conditions were not edited. Inputs were hashed before application runs: input.sha256.

## Question and method

Can an old program use state that a newer version has migrated and used? How do rollback with current state, rollback with saved old state, and an application-specific recovery differ?

One Debian 12 VM on `<HOST>`, KVM, **4096 MiB / 2 vCPU**, for the successful run. A fresh writable overlay used B's stopped, read-only `pristine.qcow2`; no retained B VM was started. The server user manager owned the VM. Host setup/run evidence: infrastructure-running.txt, setup.log, run-vm.sh. All application execution, downloads and state creation happened in the VM; writes outside the VM were limited to these E artifacts.

Pinned upstream binaries: Firefox **115.0esr → 128.0esr**, Syncthing **1.18.6 → 1.27.0**. Download checksums matched the upstream SHA-512 / SHA-256 lists; signatures were not independently authenticated. Exact URLs and checks: [setup.sh](raw-E3/setup.sh), setup.log, downloads.sha256, sources/. Actual versions also appear in the API responses. Firefox automation used geckodriver 0.34.0; the decisive downgrade probe used the ordinary Firefox CLI, independently of WebDriver.

Procedure fixed in protocol.md: initialize/use old version → clean stop and full application-state copy → start new version on that same state → verify old content and create new content → clean stop and copy → test separate rollback/recovery branches. This switches actual application binaries, not merely catalog labels; it does **not** exercise `calctl rollback`, an OS boot rollback, or package-manager hooks. B currently keeps derivative bytes across rollback (B/STAND.md, “P6 mechanisms”), so the old-binary/current-state branch isolates that compatibility question.

Full commands/API requests, responses, exit codes and timestamps: [events.jsonl](raw-E3/events.jsonl), with [event index](raw-E3/event-index.json). Reproduction harnesses: [experiment.py](raw-E3/experiment.py), [supplement.py](raw-E3/supplement.py). Main successful sequence: 08:34:08–08:34:38 UTC; supplemental control/recovery finished 08:35:31 UTC. A row marked **works** means the small workload succeeded, not universal compatibility.

## Firefox measurements

Workload: visit a loopback HTTP page; persist `before=v115` in both a cookie and localStorage; after upgrade read it, then persist `after=v128`. All profiles were disposable. State includes the generated profile databases and compatibility metadata; the content's data/derivative boundary is not settled here.

|---|---|---|---|

| Roll back only binary to 115.0esr; retain upgraded profile | Newer-profile diagnostic; requested screenshot absent; no request to `/ff-rollback-direct`; exit **0**, duration **0.019 s** | **Refuses**, despite successful process exit code | events lines 25–26 and all `fixture-request` events; [after-refusal inspection](raw-E3/ff-after-refusal-inspection.json) |

The refused attempt left all **83 regular profile files byte-identical**. All SQLite integrity checks returned `ok`: **16** databases before upgrade, **17** after upgrade and after refusal. Thus the observed result is protected refusal, not demonstrated corruption; the experiment does not show whether forcing Firefox to bypass protection would be safe. Derived comparison: [measurements.json](raw-E3/measurements.json); individual hashes, schemas and integrity results are in the inspections above. Full application-stopped snapshots (with inspection sidecars noted below): old, new.

The release-pinned [Mozilla implementation](https://raw.githubusercontent.com/mozilla-firefox/firefox/FIREFOX_115_0esr_RELEASE/toolkit/xre/nsAppRunner.cpp) agrees with the observation: a headless newer-profile refusal can return exit code zero; version checking uses `compatibility.ini`. The supplemental process environment records `MOZ_ALLOW_DOWNGRADE` absent (events line 105).

## Syncthing measurements

Workload: one local folder, no peer device; discovery, relays and automatic updates disabled. Old version indexes `before.txt` (**24 bytes**); new version reads it and indexes `after.txt` (**23 bytes**). Files are workload data, kept separate from generated config/index state. Source data stayed current during state rollback, so an old index could discover the new file by rescanning.

| Stage | Measured state / behavior | Observation | Evidence |
|---|---|---|---|
| 1.18.6, initial state | XML config version **35**; index: **1 file / 24 bytes**, sequence **1**, idle, errors **0** | Works | events line 52; [old inspection](raw-E3/st-old-inspection.json) |
| 1.27.0 on same state, then use | Config **37**, automatic `config.xml.v35` backup. Index: initially **1 / 24**, then **2 / 47**, sequence **2**, idle, errors **0** | Works; config format migrated | events lines 61, 64; [new inspection](raw-E3/st-new-inspection.json) |
| Roll back only binary to 1.18.6; retain upgraded state | Config **37** exceeds supported **35**; exits **1** before serving API | **Refuses** | events lines 71–74; [refusal log](raw-E3/st-rollback-latest.log) |
| Reopen attempted state with 1.27.0 | **2 files / 47 bytes**, sequence **2**, errors **0**; both file entries readable | Works | events lines 78–82; [recovery inspection](raw-E3/st-recovery-inspection.json) |
| 1.18.6 + complete old config/index snapshot, current source files | Scan recovers **2 / 47**, sequence **2**, errors **0** | Works; index reconstructed from still-present files | events lines 87–91; [restored inspection](raw-E3/st-restored-inspection.json) |
| 1.18.6 + **new index**, replace only config with application's `config.xml.v35` backup | **2 / 47**, sequence **2**, errors **0**; both entries readable | Works for this workload; narrower recovery than whole-state rewind | events lines 93–102; [remedy log](raw-E3/st-old-archived-config.log), [inspection](raw-E3/st-archived-config-result-inspection.json) |
| 1.27.0 after the config-only remedy | **2 / 47**, sequence **2**, errors **0**, both entries readable | Works after old-version use of index | events lines 109–117; [inspection](raw-E3/st-after-config-remedy-recovery-inspection.json) |

Migration changed more than a number: new config paths include folder `syncOwnership`, `syncXattrs`, and `xattrFilter`; `restartOnWakeup` disappeared ([schema diff](raw-E3/st-schema-diff.json)). The refused attempt left all **14 regular state files byte-identical** ([measurements.json](raw-E3/measurements.json)). No corruption was observed in the checks performed. This does **not** establish that the index's on-disk schema changed or that it is universally backward-compatible. Full closed snapshots: old, new; source files.

The pinned upstream [config loader](https://raw.githubusercontent.com/syncthing/syncthing/v1.18.6/lib/syncthing/utils.go) documents the newer-version guard and preservation of the pre-migration config. Saved source: utils.go, lines 105–132. The config-only remedy was performed on a separate copy; no format version was manually falsified and no force flag was used.

## What the data support or rule out

These are candidate approaches for the author to assess, **not adopted policy**:

| Option / claim about O7 | Evidence and limit |
|---|---|
| Binary rollback plus retained latest state always restores a usable application | **Ruled out for these version pairs under ordinary startup:** both refuse. Keeping bytes alive is insufficient to establish usability (two rollback rows above). This is not itself a paper-level `0`. |
| Restore a matching pre-upgrade application-state snapshot | **Supported in both workloads.** Firefox's new marker is absent afterward; Syncthing can recover the later file's index because current source data was retained. Snapshot boundaries and acceptable loss remain decisions. |
| Delegate compatibility handling to application-specific migration/backup mechanisms | **Supported as a limited option:** Syncthing's saved config enabled old-version use of the new index here. Firefox's guard safely refuses the tested launch but does not make old-version use work. This does not assign responsibility to application authors. |
| Check compatibility / report refusal before claiming usable rollback | **Supported by both refusals.** Firefox demonstrates why process exit code alone is insufficient. These probes do not implement a general preflight detector. |
| Force downgrade, discard state, or export/import/merge new content into old format | **Unresolved / not tested.** Refusal is not evidence of inevitable corruption; the successful config remedy is not a general migration algorithm. |

## Limitations, review and cleanup

One successful upgrade trajectory per program, two chosen historical version gaps, one inherited Debian base, root execution, clean shutdowns and tiny workloads. No crashes/concurrent writes, real user profile, extensions, passwords, long-term use, multi-peer sync, deletion conflicts, shared-state owners or per-user version coexistence. Syncthing's index is a generated derivative candidate; fixture files and Firefox content may also implicate O1/O2. No classification rule is invented. Regular-file hash equality ignores timestamps, permissions and lock symlinks. SQLite integrity checks and readable sentinels cannot prove all application semantics intact. **Inspection side effect:** the old Firefox manifest enumerated 50 regular files before read-only SQLite queries; those queries created ten empty WAL files and ten 32768-byte SHM files, so the copied snapshot contains 70 files. The database hashes matched, but this is not a byte-pristine pre-inspection directory. Snapshot restoration still worked. See the independent archive audit below.

Initial instrument defects were preserved, then corrected before the successful complete run: QEMU drive syntax (infrastructure.txt); missing HOME in a systemd setup invocation (setup-initial-missing-home.log); Python HTTP-method logging and copying Firefox's dangling lock symlink (harness-initial/, harness-second/). No application incompatibility result is inferred from those failures. An early export overlapped supplemental archive creation; the complete stopped export was repeated and verified before cleanup.

**Independent review:** a separate reviewer returned ACCEPT with the disclosed inspection limitation; no further VM probe required (review). The final independent acceptance (REVIEW-E3) remains separate. All **56 guest evidence files** matched exported SHA-256s (manifest, verification). At 08:39 UTC the E3 VM was inactive with MainPID 0; its disk and server directory were deleted (cleanup). The first cleanup process check matched its own shell command and was corrected; no unrelated VM was stopped. **The author's O7 decision remains open; hypothesis outcome `?`.**
