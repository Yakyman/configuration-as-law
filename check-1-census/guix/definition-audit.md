The decisive object is the persistent imperative package selection: profile/manifest row **guix-6633666c2c**, with selector-family row **guix-e495746cb2** representing the same mechanism. Both classifiers call these hole-two. `raw/guix/day/user-day.log` records ordinary-user `guix install hello`; `raw/guix/configuration/home/guest/.guix-profile/manifest` records its generated persistent selection; `raw/guix/guix-profiles.tsv` ties selectors to the profile. The declarations did not acquire that selection. The disputed meanings are grounded in the actual operation, not merely unknown provenance.

§5.1 says: “Derivative—an object that a described program has created itself because the object is needed for the program's operation: saved Wi-Fi networks for a network management service, extensions for a browser, a cache, a log.” It also says: “Data—what a person has created: photographs, documents, databases, and their own settings files, such as a text editor configuration.” A generated persistent personal package setting has both readings; no sentence prioritizes either. P6 says: “If the program is absent from the current generation, its derivative is moved to an archive.” Data do not receive that condition. This is the O1/O2 boundary already acknowledged in §8, not an invented new test. Under §9.2's two-classes-with-different-consequences clause, **Guix = 0**. It is one mechanism observed through two rows, not two independent replications.

The four daemon logs are different: “A derivative needed by several programs exists as long as at least one of them is present.” This P6 sentence prevents treating possible Shepherd and daemon ownership alone as incompatible classes. Source files `raw/guix/configuration/gnu/store/*shepherd-{avahi-daemon,dbus-system,guix-daemon,ntpd}.scm` identify log paths. Determining which programs actually need each file still requires evidence (O1); P6 permits shared ownership but does not automatically establish both owners. Do not label a multi-owner derivative as a two-class counterexample simply because owners differ.

For the 14 default skeleton copies, P5 says: “Any derivative and any data can be recorded in the declaration; they then become subject to it on the same terms as everything else recorded.” This is conditional. `supplementary-provenance.txt` establishes identical bytes to `/etc/skel`; `*shepherd-user-homes.scm` establishes the declared creator. Neither fact plus P5 proves a general rule that every copied output is recorded. Conversely residence in a user's home does not prove person authorship. Therefore the complete recorded-versus-hole disagreement is **not resolved** by that sentence; it should not be silently adjudicated by introducing transitive recording or home-directory ownership.

The seven classification 1 hole-none rows are grouping/provenance gaps, not seven demonstrated unclassifiable individual objects. In particular `/etc/guix` mixes ACL and signing keys; `/boot/grub` mixes boot code, generated settings and mutable state; the outside-closure store group and structural-directory group mix purposes. Unknown desktop settings provenance also cannot be repaired by the absence of edits in a short workload script. `/etc/shadow` mutability is a capability, not evidence of a password edit in this run.

Owner-name strings differ for another 33 derivative/derivative rows. Many are spelling or program-family granularity (`D-Bus`/`dbus`, `Guix`/`guix-daemon`); several require real owner evidence (Guile cache: Guile/Guix, Xauthority: Xorg+SLiM/SLiM, login logs: login/multiple login programs). They do not alter the class metric; P6 permits shared ownership but §5 supplies no lexical alias table or automatic owner-selection rule.

The ordinary-user hello output is not proved classless simply because P4 forbids its installation channel: §5 defines bypass as “a change to running components that is not recorded in the declaration.” A forbidden bypass remains describable. Whether the package-manager output itself meets the program-needs-object condition remains O1/O5/O9. Root `.ssh` is instrumentation and presents data/running-account-rule overlap, so disclose that provenance and avoid using it as the sole ordinary-use counterexample.
