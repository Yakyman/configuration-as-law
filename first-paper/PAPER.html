Configuration as Law

A hypothesis on what a declarative operating system is
Arthur Yakymenko
Preprint, draft · 18 November 2026 · Hypothesis, version 1; no checks have been run yet

Abstract

Operating systems in which the computer is specified by a description rather than a history of manual changes are called declarative. However, in the literature we found, there is no definition of a declarative operating system as a list of required properties. Research on configuration management describes individual properties—convergence, idempotence, determinism—or the rules of individual tools. Work that describes the operating system as a whole leaves the mutable state of the running machine outside the model. Individual parts of the answer are known: complete control of configuration without manual intervention, a read-only system root, and deletion of dependent objects after their owners disappear. But in the sources we found, these have not been brought together into a single definition. We ask: what is a declarative operating system, and what properties must it have? In response, we propose the seven-property hypothesis “Configuration as Law”. The declaration describes everything that runs on the computer, and everything described is guaranteed to be present on it. Everything else on the computer is either a derivative of a described program, that is, something the program created for its own operation, or the person's data. No program can change the system by bypassing the declaration; a bypass is possible only explicitly. We introduce concepts, work through an example, compare the hypothesis with existing systems, list open problems, and describe checks that could refute it. No checks have been run yet.

Keywords: declarative configuration, configuration management, operating systems, mutable state, reproducibility.

1. Introduction

The state of a computer can be specified in two ways. With imperative configuration, an administrator performs a sequence of actions: installing programs, editing files, enabling services. The machine's state results from these actions and their order. With declarative configuration, the administrator describes the required final state, and a tool derives the actions that lead to it; Anderson and Couch define declarative configuration as specifying “the desired final state” [5]. The approach rests on the separation that Kowalski drew for algorithms: logic “determines the meaning of the algorithm”, whereas control “only affects its efficiency” [48]. In system configuration, this separation means that a person describes what should be, and the tool decides how to achieve it.

A number of operating systems call themselves declarative. NixOS lists this word among its main features on the project's home page [52]. GNU Guix builds a system from an operating system declaration “that specifies user accounts, system services, and other settings” [20]. Both systems rely on the functional software deployment model developed by Dolstra [26, 38].

However, in these systems the description does not cover everything that runs on the computer. Alongside declarative software installation, the NixOS manual describes “ad hoc” installation, in which programs are installed, updated, and removed with the nix-env command, and notes that this is the only method for users without root privileges [53]. By default, user accounts in NixOS can be created with the ordinary commands useradd and groupadd [54]. The Kubernetes documentation lists as an advantage of declarative configuration that changes made directly to live objects are preserved even if they have not been incorporated into the configuration files [50]. If something runs on the machine that is absent from the description, the description ceases to be a reliable source of information about the machine.

We found no definition in the literature by which one could decide whether a system is declarative. Research on configuration management formulates individual properties: convergence [9, 40, 42], idempotence [42, 44, 64], and determinism and monotonicity of the configuration language [35]. Proposals for declarative operating systems leave the mutable state of the running machine outside the model [25, 28, 29]. In 2004, Anderson and Couch described the theory of configuration languages as “only in their infancy” and listed the question “What is a “configuration” ?” as open [5]; in 2017, Anderson wrote that declarative configuration languages “have not been widely studied in any formal way” [4].

Individual parts of the answer are nevertheless known. Anderson called a system that controls the entire configuration of machines without manual intervention “proscriptive” [2]. The Stateless Linux project proposed a system root that was read-only even for root [62]. Kubernetes deletes a dependent object when all its owners disappear [49]. We found no work that brings such parts together into a definition of a declarative operating system.

In this paper, we ask: what is a declarative operating system, and what properties must it have? Our contributions are as follows:

  • we formulate the hypothesis “Configuration as Law”—a definition of a declarative operating system through seven properties (Section 5);
  • we introduce the concept of a derivative—an object that a described program creates for its own operation—and a rule by which everything on the computer that is not recorded in the declaration is either a derivative or the person's data (Sections 5 and 6);
  • we show which properties of the hypothesis already have predecessors and which—classification of what is not recorded, a law for all paths of change, and a lifecycle of derivatives tied to generations—do not appear in the sources we found (Sections 3, 5.4, and 7);
  • we list open problems that the hypothesis does not yet solve (Section 8) and describe checks that could refute it, with failure conditions fixed in advance (Section 9).

Section 2 introduces the concepts on which the paper relies. Section 3 reviews related work. Section 4 states the problem. Sections 5–9 present the hypothesis, an example, a comparison, open problems, and a plan for checks. Section 10 discusses limitations, and Section 11 concludes.

2. Background and concepts

2.1. Imperative and declarative configuration

A 2010 survey of configuration management tools distinguishes them by their input language: “Tools that use a declarative input language enable to express the desired state of the computer infrastructure” [24]. The OpenGitOps principles define a declarative description as a configuration that describes the desired operational state of a system “without specifying procedures for how that state will be achieved” [55]. Both definitions concern the form of the description and say nothing about what the description must cover.

Anderson separates two properties that are often conflated. A declarative system accepts a description of the desired state but does not have to control the entire configuration. He gives a different name to a system that does: “If a configuration system controls the entire configuration for a set of machines, with no manual intervention, then it is known as proscriptive” [2].

The works examined provide no common criterion for being declarative: the same tool, Chef, is called an imperative language in the 2010 survey [24] and classified as a declarative technology in the 2020 systematic review [71]. The authors of µPuppet call Chef declarative with respect to the target state and imperative with respect to the order of actions [35].

2.2. Congruence and convergence

Traugott and Brown distinguish modes of machine management [67]. Under convergence, the tool gradually brings the machine closer to a baseline, which is itself “characteristically an incomplete description of machine state”. They call the strictest mode congruence: “maintaining production hosts in complete compliance with a fully descriptive baseline”. Here the baseline describes the part of the disk owned by root and managed by the administrator; user data and logs are excluded: “we neglect user data and log files” [67]. The authors of NixOS use this concept: “Disregarding mutable state, NixOS has a congruent model” [29].

2.3. Desired state and its boundaries

In OpenGitOps, desired state is a collection of configuration data that is “sufficient to recreate the system so that instances of the system are behaviourally indistinguishable”; it “generally does not include persistent application data” [55]. Morris decomposes the state of an immutable server into “base image + automated configuration management + data” and includes in data “runtime state, other runtime-generated data such as log files” [51]. Google's guide to systems operations requires configuration to be separated from data [22].

File layout standards divide state by purpose. FHS 3.0 defines state in /var/lib as follows: “State information is data that programs modify while they run”, and says of the cache in /var/cache: “The application must be able to regenerate or restore the data” [33]. The UAPI.9 specification leaves persistence of /var optional: “Persistency is recommended, but optional, to support ephemeral systems” [68]. The XDG Base Directory Specification 0.8 divides user files into configuration, data, cache, state, and runtime files; state differs from data in being “not important or portable enough to the user” [72].

Thus, the separation of configuration, data, and state is accepted, but the boundaries are drawn differently and according to different criteria: Morris classifies logs as data, whereas FHS and XDG distinguish them separately; FHS and XDG classify by purpose and storage location, rather than by who created an object and why. We found no rule by which every object on a computer belongs unambiguously to one class.

3. Related work

3.1. Research on configuration management

In 2003, Couch and colleagues proposed building configuration from “closures”—predictable subsystems: “A closure is a highly predictable subsystem of an otherwise open system”. Their first axiom requires a set of agents to be “convergent, consistent, aware, and atomic”, but the authors acknowledge: “We have not yet precisely determined what consistency means” [17]. In 2006, Burgess and Couch introduced the concept of a promise: “A promise is a specification of future state or behavior from one autonomous agent to another” [11]; promise theory formalizes convergence [9].

In his 2013 thesis, Hewson states that “All declarative configuration systems are based on two important principles”—idempotence and convergence [42]. Hanappi and colleagues give a sufficient condition for convergence: “A configuration specification whose resources are idempotent and preserve their respective ancestors and non-related resources is convergent” [40]. ConfSolve lists “Order never matters” among its design principles [43]. Hummer and colleagues show that “idempotence is a requirement for convergence” [44]. For a subset of Puppet without exec commands, Shambaugh and colleagues prove that such descriptions “are deterministic and idempotent, which are both fundamental properties of correct Puppet manifests” [64]. The authors of µPuppet find that determinism and monotonicity provide only “some justification for the claim that µPuppet is ‘declarative’”, and write: “Further work is needed to identify and prove desirable properties” [35].

A number of works show where configuration management models make assumptions about the running machine. Couch and Sun acknowledge that their reproducibility model “does not model state changes due to usage and – more important – due to unauthorized intrusions” [18]. In 2008, Couch notes that tools such as BCFG2, Puppet, and Cfengine “utilize an operational semantic model similar to that of x=1 in C”, that is, they describe file edits rather than system behavior [15]; in 2010, he concludes that “a configuration description cannot be more than a statement of intent rather than fact” [16]. Burgess and Couch show that a convergent change “is a many-to-one transition, and is hence non-invertible without a history” [12]. The survey by Delaet and colleagues states: “No tool has support for the data that is on the managed machines” [24].

The question of authority has been examined separately. In 2008, Anderson pointed out that restricting permissible changes requires “tracking the provenance of each parameter value, and performing the composition in a trusted environment” [3]. Vanbrabant and colleagues developed access control for the Puppet language in which “Superusers are allowed to make all changes”, and themselves showed that “It is possible to circumvent the authorisation using simple attacks” [69].

A number of works explicitly point to the incompleteness of the field. In his 2015 thesis, Herry writes: “We are not aware of any document that provides the formal semantics of the declarative configuration languages that are used in real "production" system” [41]. In 2017, Anderson noted that such languages “have not been widely studied in any formal way” [4]. A systematic review of research on infrastructure as code defines it as “the practice to automatically configure system dependencies and to provision local and remote instances” [61]; this definition requires neither completeness of the description nor a prohibition on changes that bypass it. The principles adopted by the authors of configuration languages contradict one another: CUE prohibits overriding values [21], whereas Jsonnet requires the ability to override them [47].

3.2. Functional and declarative operating systems

In 2004, Dolstra and colleagues proposed Nix, a deployment system that computes unique installation paths for components using cryptographic hashes [27]. In his 2006 thesis, Dolstra divides services into “software components, static configuration and data, and mutable state. The first two aspects can be managed using Nix” [26]. In their 2007 paper, Dolstra and Hemel extend the model to system configuration, with the qualification: “Mutable state, such as most everything in /var, falls outside the scope of this approach”; they also distinguish being declarative from their model: “Configuration tools such as Cfengine and LCFG are declarative, but stateful” [28].

In the 2010 NixOS paper, all static parts of the system—packages, configuration files, startup scripts—are built by pure functions and are immutable. The authors write: “NixOS does not have any mechanism to deal directly with mutable state, such as the contents of /var”; such state is managed by the activation script and services “in a standard, stateful way”, and “the running of a system (as opposed to the configuration) is inherently stateful”. The model also assumes build purity, although “current operating systems cannot enforce this” [29].

GNU Guix brings the same model to Scheme: building and installing a package are treated as “a pure function, without any side effects” [19], and the entire system is created from an operating system declaration [20]. At Microsoft Research, DeTreville proposed “a declarative system model that completely and precisely specifies the system as a whole” for the Singularity operating system, and stated: “Our current system instances are static, but we plan also to support dynamic instances to model the system’s runtime state” [25]. In Singularity itself, “No code is allowed to run on a Singularity system without a manifest” [45].

3.3. Image-based systems

Red Hat's 2004 proposal for Stateless Linux lists “Some ideal properties of an operating system”, including “single computers should never be modified”; the system root is read-only, and “even root can only write to /tmp and the home directory” [62]. In 2014, Poettering described a system that “never stores /etc or /var on persistent storage, but always comes up with pristine vendor state” [59]; in 2022, he described a system with an immutable /usr tree that “can then be mounted read-only into the writable root file system”, and with a factory reset [60]. In the ParticleOS project, “users build the ParticleOS image themselves and sign it with their own keys” [58]. In all these works, the initial state is specified by a system image rather than a description written by a person for a particular machine.

Systems based on OSTree separate the immutable image from mutable state. In OSTree, “/etc is a regular writable directory”; the contents of /var from the image are copied only into an empty directory, and during an update “Any files which already exist will not be updated” and “Any files which are deleted in the new version will not be deleted on existing systems” [56]. In Fedora Atomic Desktops, “The /etc and /var directories are respectively used to store configuration files and runtime state and are thus writable” [30]; rpm-ostree allows temporary changes to /usr, and “The changes here will not persist across reboots” [63]. Fedora CoreOS configuration is set once: “Ignition runs only once during the first boot of the system” [31]. In Chromium OS, the root is read-only, while the state partition is mounted writable and used “for all state that needs to be stored locally” [13].

Specialized server systems go further in exercising control. In Talos Linux, “Everything which can be configured in Talos is done through a single YAML manifest”, and the capabilities to load kernel modules and reboot are unavailable: “any process including privileged Kubernetes pods will not be able to get these capabilities”; at the same time, the documentation describes a debug container that “runs privileged with host PID and network namespaces” [65]. In Bottlerocket, settings are described by a model—“Modeled configuration that's automatically migrated through updates”—but files in /etc “are regenerated when a setting changes, but otherwise not monitored” [10].

3.4. Tools that bring a live system into correspondence with a description

The aconfmgr tool for Arch Linux captures differences between a live machine and a description and applies them back; in it, “the absence of an item in the configuration file indicates its absence on the system”. Direct changes to the system are permitted, and files that belong to no package are excluded by rules written by the user [1]. The Tortoise tool observes commands that an administrator executes in a shell and “automatically repairs the higher-level specification written in the configuration language”; the authors qualify this: “we do not detect changes made by background processes” [70]. The impermanence module for NixOS “Lets you choose what files and directories you want to keep between reboots - the rest are thrown away” [46]; Christensen describes the same technique: “My technique is to explicitly opt in and choose which state is important, and only keep that” [14]. Morris describes an immutable server that, after deployment, “is never modified, merely replaced with a new updated instance” [51]. These techniques keep the system close to the description—by capturing differences, incorporating them into the description, or erasing them—but provide no rule for which state remains outside the description and why.

3.5. Mechanisms for the lifecycle of state

Several systems tie state to its owner. In systemd, a service declares its state, cache, and log directories, but “The directories specified with StateDirectory=, CacheDirectory=, LogsDirectory=, ConfigurationDirectory= are not removed when the unit is stopped” [66]. In Kubernetes, an object can have multiple owners, and “the dependent is subject to deletion once all owners are verified absent” [49]. Flatpak allows an application to write only to its own data directory and deletes these data when the application is uninstalled with --delete-data [34]. Debian policy requires that configuration files “must be preserved when the package is removed, and only deleted when the package is purged” [23]. In pacman, configuration files modified by the user are preserved during an update, and “The user must then manually merge any necessary changes into the original file” [57].

3.6. Industry principles

The OpenGitOps principles require desired state to be described declaratively, stored with a complete version history, automatically pulled by software agents, and continuously applied by them to the system [55]. The Kubernetes design principles require that “All APIs should be declarative” and that functionality be “level-based”, that is, work correctly from the desired and observed state [39]. At the same time, Kubernetes preserves changes made to live objects by bypassing configuration files [50]. In selfHeal mode, Argo CD starts synchronization when the live cluster diverges from the description in Git [7]; for resources that belong to no application, it allows detection, inspection, manual deletion, and warnings, but does not prohibit their creation [8]. Google's guide lists three requirements for configuration systems, including hermetic configuration evaluation for rollback, and specifies that they are additional to “generic ideal requirements” [22].

3.7. Review findings

Some of the properties we propose have predecessors. Complete control of configuration without manual intervention has been called “proscriptive” [2]; the rule “what is absent from the description is absent from the system” is implemented for managed objects in aconfmgr [1]; a root that is not writable even by root was proposed in Stateless Linux [62]; capabilities are restricted even for privileged processes in Talos [65]; deletion of a dependent object after all its owners disappear is present in Kubernetes [49]; access control over configuration has been studied for Puppet [69].

Work that describes the operating system as a whole leaves mutable state outside the model, while industry systems and image-based systems allow changes that bypass the description, warn about them, revert them through synchronization, or erase them, but do not prohibit them. We found none of three things in these works: a list of required properties of a declarative operating system; a rule by which any object on the computer that is not recorded in the declaration belongs to a class with a defined owner; or a lifecycle of such objects tied to system generations. Nor did we find a proof that such a definition is impossible. The review covers the sources we found and read and is not a systematic review of all the literature.

4. Problem statement

Research question:

What is a declarative operating system? What properties must it have?

Scope. We consider the operating system of an individual computer—a workstation or a server—with one or more users. The hypothesis is not tied to a particular operating system; the checks are planned for Linux. Cluster orchestration and distributed configuration are outside the scope of this work. We deliberately do not discuss the declaration's language or format: decisions about system design depend on the answer to the question, not the reverse.

What counts as an answer. A list of properties that meets three conditions: the properties allow any object on a real computer to be assigned to a specific class; a system with these properties can be built and used in everyday work; and existing systems that call themselves declarative can be assessed against each property separately.

5. The “Configuration as Law” hypothesis

5.1. Concepts

  • Declaration—a collection of files that a person has designated as the primary description of the computer. A declaration may consist of many files, but it forms one description and one source of truth about the system.
  • Running components—users and the rules under which they operate, programs, drivers, and services.
  • Derivative—an object that a described program has created itself because the object is needed for the program's operation: saved Wi-Fi networks for a network management service, extensions for a browser, a cache, a log. Code executed within a program is its derivative. The term is unrelated to the concept of a derivation in Nix, where it denotes a build description.
  • Data—what a person has created: photographs, documents, databases, and their own settings files, such as a text editor configuration.
  • Generation—a version of the system resulting from a new application of the declaration; it is possible to return to saved generations.
  • Bypass—a change to running components that is not recorded in the declaration.

5.2. Properties

P1. Completeness. Everything that runs on the computer is recorded in the declaration. The only exception is an explicit bypass (P4): through a line in the declaration or through manual actions by a person with root privileges. In both cases, responsibility for the bypass lies with the person, not the system.

P2. Guarantee. Everything explicitly recorded in the declaration is present on the computer.

P3. Classification of the remainder. Everything that is on the computer and is not recorded in the declaration is either a derivative of a recorded program or the person's data. A derivative is not a second source of truth about the system: only the declaration states what runs on the computer.

P4. Law. The system provides no path for changing running components by bypassing the declaration. A program, including one running with root privileges, changes the system only by writing to the declaration: an installer does not install a program by bypassing the declaration but adds it to the declaration. A bypass is possible only explicitly: through a line in the declaration itself that permits it, or through manual actions by a person with root privileges. In both cases, responsibility for the bypass lies with the person, not the system.

P5. Inclusion. Any derivative and any data can be recorded in the declaration; they then become subject to it on the same terms as everything else recorded.

P6. Lifecycle of a derivative. A derivative exists as long as its program is present in the current generation or in one of the saved generations. If the program is absent from the current generation, its derivative is moved to an archive. A derivative needed by several programs exists as long as at least one of them is present. Whether to keep the archive indefinitely or delete it is a setting recorded in the declaration.

P7. Authority. The root declaration belongs to root and serves as a constitution. Each user has a personal declaration, which relates to the root declaration as a code of law relates to a constitution and cannot contradict it. By default, the user's permissions are determined by ordinary Unix permissions; root can restrict the personal declaration with an allowlist or a denylist. Root's own privileges are not restricted, and the system does not take them away from the person.

5.3. Consequences

  • Understanding. If no explicit bypass has occurred, reading the declaration is sufficient to find out what runs on the computer (P1, P2, P4). A line permitting a bypass states only that the bypass is permitted; it does not enumerate what has actually been launched under that permission.
  • Reproducibility. The same declaration on another computer yields the same recorded components; what is not recorded or ran through an explicit bypass is not expected on the other computer (P1, P2). The hypothesis does not yet define how to transfer derivatives and data (Section 8, O8).

5.4. Relationship to established concepts

Properties P1 and P2 together correspond to Traugott and Brown's congruence, applied to running components [67]; P1 together with P4 is close to what Anderson calls “proscriptive” configuration [2]. We distinguish the hypothesis from these concepts in three respects.

First, the hypothesis does not exclude the rest of the computer's contents from its scope, as Traugott and Brown do with data and logs [67] and the authors of NixOS do with mutable state [29], nor does it leave these contents to exclusion rules written by the user, as in aconfmgr [1]. Every object not recorded in the declaration is assigned to an owner: a recorded program (a derivative) or a person (data)—property P3.

Second, property P4 makes the prohibition on bypass a property of the system itself for all paths of change, rather than a matter of administrative discipline. A change that bypasses the description ceases to be an admissible mode of operation, as it is in Kubernetes [50], when installing programs with the nix-env command in NixOS [53], and in aconfmgr, where direct changes are subsequently captured in the description [1]. Unlike Stateless Linux, where even root is restricted [62], the hypothesis leaves root privileges unrestricted and places responsibility for a manual bypass on the person (P4, P7).

Third, property P6 ties the lifecycle of a derivative to system generations. The multiple-owner mechanism in Kubernetes [49] comes closest to the rule for a shared derivative, but it deletes dependent objects rather than moving them to an archive and is not tied to generations. Service state directories in systemd are not removed when a service stops [66], while Debian and pacman policies preserve package configuration files according to their own rules [23, 57].

8. Open problems

Version 1 of the hypothesis leaves the following questions open. We name them explicitly because these are precisely the points on which the checks may refute the hypothesis.

  1. O1. A criterion for a derivative. A derivative is defined by the fact that a program needs the object in order to operate. This is the program's intent, which cannot be observed directly. An observable criterion is needed: for example, which program created the object or where it is stored. The FHS and XDG standards classify by directory purpose [33, 72], and Flatpak and Kubernetes by an explicitly specified owner [34, 49]; none of these criteria derives the program's need from observation.
  2. O2. The boundary between data and a derivative. A person creates a document, but a program writes it to disk. A person writes an editor configuration, but the editor executes it, and code executed within a program is, by definition, its derivative. XDG distinguishes state from data by its importance and portability to the user [72], while Debian policy classifies some executable scripts as configuration [23]. A rule is needed that resolves such cases unambiguously.
  3. O3. The status of recorded data. Under P5, data can be recorded in the declaration and then become subject to it. Do they remain data after this, or do they become part of the system?
  4. O4. A person and a program with root privileges. Under P4, a person with root privileges can bypass the declaration manually, whereas a program with the same privileges cannot. How does the system distinguish these two cases? And what happens to the guarantees of P1 and P2 during an explicit bypass—through a line in the declaration or manually as root: must the system keep track of what runs through the bypass and report divergence from the declaration? Tortoise explicitly limits observation to the administrator's session and does not see background processes [70].
  5. O5. Launching and creation. Does a program launched by another program, such as a shell, become its derivative?
  6. O6. An archive without instructions. What happens to a derivative's archive if the declaration says nothing about it?
  7. O7. Rollback and compatibility. Who is responsible for ensuring that, after a rollback, an old version of a program can read a derivative written by a new version? A convergent change is irreversible without a history [12], and in OSTree the /var directory is shared across system versions and is not reverted when the image is rolled back [56].
  8. O8. Transferring derivatives. Should derivatives be transferred to another computer separately from the declaration, and if so, how? The 2010 survey notes that none of the tools examined supports data on managed machines [24].
  9. O9. What “runs” means. Do running components include everything installed or only what has been launched? What about firmware and what is stored off-disk, for example in board memory or a TPM module?

9. Plan for checks

9.1. General rules

For each check, its failure condition is fixed before it begins. The outcome of each check is 1 (the hypothesis withstood the check), 0 (it did not), or ? (insufficient data). We distinguish two kinds of failure. A counterexample to the definitions—an object that the definitions cannot classify (Check 1), or a requirement that contradicts another requirement—yields 0 for the hypothesis. A prototype failure yields 0 for the hypothesis only if it is shown to follow from the property itself rather than the prototype's design; otherwise, it is an implementation defect, and the outcome for the hypothesis is ?. If the definitions change after the results become known, this produces a new version of the hypothesis; it is checked against objects and machines that the previous version has not seen. All records of checks are dated and are not deleted.

9.2. Check 1: census

Aim. Check that the concepts in Section 5 allow unambiguous classification of all objects on a real computer (P1, P3).

Objects. Two levels: running components—packages, services and timers, processes, accounts, kernel modules and drivers; and stored objects that belong to no package, grouped by directory, for example by a program's directory in /var/lib or ~/.config.

Procedure. The inventory is compiled using system facilities: the package database, service manager, process list, account database, and a list of files that belong to no package. Each object is classified twice, independently, using the written definitions in Section 5. Agreement between them is measured by the proportion of matching decisions and Cohen's kappa.

Failure condition. An object is found on either machine that, under the definitions, belongs to no class or belongs to two classes with different consequences, or the two classifications assign the object to different classes and the text of the definitions does not resolve the disagreement.

Weaknesses. Both machines belong to one person, so conclusions about other computers are limited. The two classifications may share errors; their independence reduces this possibility but does not eliminate it. The system facilities used for the inventory may not see some objects, such as firmware variables (O9).

9.3. Check 2: law

Aim. Check that a system with property P4 can be built and used in everyday work.

Object. A Linux prototype in a virtual machine.

Procedure. The paths by which a program reaches the computer are derived from a list of installation channels: the system package manager; programming language package managers (pip, npm, and others); application packages (Flatpak, AppImage); direct downloads of programs and archives; building from source code in the home directory; user service managers and schedulers (systemd --user, cron); interpreters executing user scripts; and extension mechanisms within programs. Under P3, extensions within programs are derivatives and do not count as bypasses; execution of scripts by an interpreter is a case of open problem O5, and its outcome is recorded as ? if the definitions do not resolve it.

Failure condition. At least one channel installs or launches a program although the declaration does not permit it and the person did not do it manually with root privileges; or explicit permission through a line in the declaration does not take effect; or an ordinary action by a person—installing a program, updating the system, connecting to a Wi-Fi network, connecting a Bluetooth device, working in a browser—cannot be performed without bypassing the declaration.

Weaknesses. The virtual machine has no Wi-Fi or Bluetooth hardware, so these actions are checked on a real computer. The prototype covers part of the operating system rather than the entire system.

9.4. Check 3: reproducibility

Aim. Check the consequence stated in Section 5.3.

Procedure. The same declaration, without lines permitting a bypass, is applied to two clean machines; the running components are compared.

Failure condition. The running components differ, and the difference is not explained by differences in hardware.

9.5. Check 4: lifecycle of a derivative

Aim. Check property P6 on the prototype.

Procedure. A program with derivatives is removed from the declaration; all saved generations in which it was present are then deleted; a derivative needed by two programs is checked separately when one of them is removed. The experiment is repeated with two values of the archive setting: keep indefinitely and delete.

Failure condition. A derivative is deleted while its program is present in the current or a saved generation; or a derivative remains active even though no program that needs it is present in the current generation, and it has not been moved to an archive; or a shared derivative is moved to an archive, deleted, or made inaccessible while a program that needs it is present in the current generation; or the fate of the archive differs from the setting.

9.6. Check 5: authority

Aim. Check property P7 on the prototype.

Procedure. A user adds a program to their personal declaration, then attempts to record something in it that contradicts the root declaration; root restricts the personal declaration using an allowlist and a denylist.

Failure condition. The personal declaration was able to contradict the root declaration; or a list-based restriction does not take effect; or, in the absence of lists, the user cannot do what ordinary Unix permissions allow; or the system restricts root's own privileges.

Coverage of the plan. Checks 2, 4, and 5 are performed on one prototype, so their failure, without proof that it follows from the property itself, indicates a defect in the prototype rather than the falsity of the hypothesis (Section 9.1).

10. Discussion and limitations

Novelty. Individual properties of the hypothesis have predecessors: complete control of configuration [2], an immutable root [62], absence semantics [1], multiple owners of a dependent object [49], and access control over configuration [69]. What we consider new is their combination into a definition of an operating system, together with what we did not find in the predecessors: a rule assigning every object not recorded in the declaration to an owner (P3), a prohibition on bypass as a system property for all paths of change (P4), and a lifecycle of derivatives tied to generations (P6). This is an assessment of the sources we read, not a proof of novelty: a search does not prove that no such source exists.

Applicability of the definitions. The definitions of a derivative and data depend on who created an object and why (O1, O2). If two independent classifications diverge, version 1 of the hypothesis is inapplicable in practice. Check 1 is designed to reveal this before a system is built according to the hypothesis.

Root privileges. Unrestricted root privileges are a condition of the hypothesis. Distinguishing a person's manual actions from the actions of programs with the same privileges remains an open problem (O4).

Scope. The hypothesis is formulated for an individual computer. We have not considered its applicability to clusters and distributed systems.

Quotations. Every quotation was checked against its primary source.

11. Conclusion

We asked what a declarative operating system is and what properties it must have, and found no answer in the literature. The “Configuration as Law” hypothesis answers this question through seven properties. The description must cover everything that runs on the computer, and everything described must be present on it. Every object not recorded in the declaration belongs either to a recorded program or to a person. Changing the system by bypassing the description is possible only explicitly. The hypothesis differs from established concepts—Traugott's congruence and Anderson's complete control of configuration—in its classification of what earlier work excluded from scope, its prohibition on bypass as a system property, and its lifecycle of derivatives. The next step is the checks described in Section 9; their outcomes will be published with the next version of the hypothesis.
