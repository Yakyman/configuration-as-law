# Bounded documentation follow-up

No classification rows were changed. These findings correct factual overstatements in the earlier part.

## GCC and CMake purpose

- [GCC introduction](https://gcc.gnu.org/onlinedocs/gcc/G_002b_002b-and-GCC.html): “GCC is an integrated distribution of compilers for several major programming languages.” Its documented purpose is compilation. The previously cited output-options page establishes generation of object files and linked executables; it does not establish package installation/removal as GCC's purpose.
- [CMake command manual](https://cmake.org/cmake/help/latest/manual/cmake.1.html), Description, calls it a “cross-platform buildsystem generator CMake” and describes its additional script actions as intended “to support their builds”. This is documentation of a dedicated build tool with scripting facilities, not documentation calling CMake a general-purpose shell or scripting program.
- The same manual, Install a Project: “CMake provides a command-line signature to install an already-generated project binary tree:”. Its `cmake --install <dir>` operation directly performs installation after building without requiring the generated build system or native build tool. The manual separately documents `-P` script processing, with no configure/generate step and no cache modification.
- Consequently, the earlier factual premise that CMake's only relevant functionality was general script execution was incomplete. Its documented installation purpose is affirmative evidence for considering S8.1-7 independently of the installing-and-removing condition in S8.1-4. The documentation supports distinguishing CMake itself from a generic shell that merely executes a user-authored install command. The classification consequences for C5.2/C5.3 are left to review.

## Manual path-only .pth files

The [site documentation](https://docs.python.org/3/library/site.html) says that path entries extend `sys.path`, while import lines “are executed with `exec()`.” Path-only content is read as values, not executed as code. This documentation does not establish who created a particular file. A manually supplied path-only file cannot be called program-created as a factual inference. S8.2-14 may classify a personal-program value as that program's record regardless of writer; if that rule is applied, it must be cited directly rather than incorrectly asserting the Q4 program-created origin. This is distinct from determining whether a particular chosen path value launches something.

## Cached wheels and executable ZIP members

The [wheel specification](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) describes wheels as ZIP archives and, in its direct-import FAQ, explicitly confirms: “a subset of wheel files do support being placed directly on `sys.path`.” A wheel is therefore not established to be inert merely by its compressed representation.

The [zipimport documentation](https://docs.python.org/3/library/zipimport.html) states: “This module adds the ability to import Python modules (`*.py` (some matches not published: already-public inputs and their preparation records) (some matches not published: pre-observation input or preparation record), `*.pyc`) and packages from ZIP-format archives.” It also explains that ZIP paths can be added to `sys.path`, including paths to subdirectories inside the archive; dynamic extension modules cannot be ZIP-imported. This supports direct execution of suitable Python code members from a retained wheel without extraction, conditional on compatible contents and interpreter support. It does not show that every arbitrary wheel can run unchanged: native extensions and packages requiring installed external resources are distinct.

The [pip caching documentation](https://pip.pypa.io/en/stable/topics/caching/) distinguishes locally built wheel files from HTTP response cache entries. It confirms persistent reuse of successful source-distribution wheel builds and immutable VCS builds; wheels from a direct local project path are not retained across invocations by that mechanism. The documented Linux cache root is `$HOME/.cache/pip`, respecting `XDG_CACHE_HOME`; exact internal paths are implementation details. A cache label therefore does not establish Q4 for each retained object. A retained compatible wheel's executable Python members require the earlier Q2 check; HTTP metadata and non-code administrative records can still reach Q4. The earlier blanket inert-wheel-cache description was unsupported and should not be relied upon.
