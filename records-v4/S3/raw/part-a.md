## Text and notation

D0 is the declaration of the previous completed application reported successful. D1 is the requested updated declaration. X0 and X1 name states satisfying their respective requirements. Where a partial-change argument uses two changed objects x and y, its explicit premise is that their old and new line requirements conflict: x must have x0 under D0 and x1 under D1, with x0 different from x1; similarly y0/y1. This notation instantiates the already committed several-object event; it does not add a new event or assume that every declaration specifies exact values. When lines permit both actual values, changing those values need not violate P2.

The following quoted clauses define the references used in every table's duty column. They are requirements, not claims that an implementation satisfies them.

- ACTIVE, S8.1-14: “The declaration in force is the declaration of the last application that the system reported as successful [3, Section 3].”
- TIME, S8.3-1: “The properties concern the computer at any moment after a completed application of the declaration, provided there was no breaking.”
- LINE, S8.1-12: “The required state of a recorded object is stated by its line.”
- P1, S8.3-4: “**P1. Completeness.** Everything that is installed and every setting, when in force on the computer, are recorded.”
- P2, S8.3-5: “**P2. Guarantee.** Everything recorded in the declaration is in force on the computer as its line requires.”
- P4a, S8.3-6: “**P4. Law.** The system provides no ordinary path for changing what is installed and settings past the declaration.”
- P4b, S8.3-7: “Its tools for installation and configuration record changes in the declaration even when they run with superuser privileges: an installer does not install a program past the declaration but adds it to the declaration.”
- P4c, S8.3-8: “What is installed and settings can be changed past the declaration only by breaking.”

Duty bundle R(D) means, throughout the relevant moment by TIME: P1 covers every actual in-force installed object and setting; P2 requires every recorded requirement of the in-force D to hold as LINE specifies; P4a/P4b/P4c require an ordinary tool route to record the change rather than bypass the declaration. P1, P2 and P4 remain separate: a value differing from an exact line proves P2 false without automatically proving every clause false. In particular, whether a new object's provenance gives it coverage requires S8.2-16 or S8.2-17, not an assumption that every new object is unrecorded.

The relevant coverage sentences are S8.2-16: “What is installed is recorded by one of three lines: a line of its own; the line of the package as part of which it was obtained; a line from which the system itself built or obtained it—a compiled copy, a generated list, a package installed as a dependency of a recorded package.” S8.2-17: “A setting is recorded by a line of its own; a default value obtained with a package or created during its installation is covered by the line of the package.”

## Conditional incompatibility proof, with objections

1. An earlier application is completed and reported successful, and the update is ordinary rather than breaking. TIME (S8.3-1) applies throughout the later update. Its wording does not say only after the most recent operation ends. **Objection:** the updating phase temporarily suspends the properties. **Reply:** no quoted sentence supplies that suspension; ordinary updating is also expressly on the work list in Appendix A.4.3. Calling the attempted operation breaking would contradict its stated ordinary-tool premise, rather than refute this argument.
2. Before any later successful report, ACTIVE (S8.1-14) makes D0 the in-force declaration. LINE (S8.1-12) and P2 (S8.3-5) require its old values. **Objection:** merely editing pending files already changes the active requirements. **Reply:** the definition's operative event is the successful application report, not the edit. Section 8.5 expressly excludes when an edit takes effect from the definition; inventing a particular edit mechanism is neither necessary nor justified here.
3. If an ordinary implementation changes a requirement from x0 to incompatible x1 before that report, P2 fails at the changed moment. If it reports D1 first, P2 fails while any new requirement remains missing. P1 can additionally fail if an actual in-force object lacks any allowed coverage; P4 can additionally fail if an ordinary path changes installed objects or settings past the declaration. Neither additional failure is automatic merely because P2 failed. **Objection:** no person or program can observe this interval. **Reply:** TIME says at any moment, while the force definitions concern actual state, not observations: S8.1-10: “A setting is in force if it has its value.” S8.1-11: “A service is in force if it is enabled; an account, if it exists.” Observer exclusion alone leaves those facts unchanged.
4. If interruption or rollback follows the violation, the earlier required moment remains one at which P2 was false by TIME. **Objection:** rollback ultimately restores X0. **Reply:** endpoint restoration addresses I4 but not I1–I3; neither P2 nor TIME grants an interval for eventual convergence.
5. **Strongest objection to a universal conclusion:** the system changes all required effective state, the recorded declaration, and its successful-application report as one indivisible event. Before it, D0 and X0 agree; after it, D1 and X1 agree. P4b can hold because the tool records the same change in that event. No cited sentence requires those components to change in separate events. Section 8.5 leaves mechanism, declaration representation, generations, rollback and edit activation out of the definition. **Disposition:** this objection defeats the inference that the definitions force failure whatever the system does. It is not proof that a real useful system can implement the event.

A second objection is that a requested several-object update could use intermediate successful applications Dm, each with its own accurately reported change. ACTIVE then selects the last such Dm, not D0, and P2 checks Dm's actual requirements. The task does not ban intermediate applications. This is an alternative implementation of the same committed update, not an extra event to test; the draft does not supply new declarations as an experiment. It further prevents a proof based solely on the number of changed objects. It still requires each actual transition to satisfy the properties, so it does not itself establish feasibility.

### Why common substitutes do not answer the strongest objection

- **Activation alone is indivisible:** insufficient if reporting follows later; A3 remains.
- **Observers are paused:** insufficient if actual settings or accounts change in the pause, by TIME and the force definitions.
- **A new installed generation is staged but not selected:** it cannot simply be omitted from P1. S8.1-9: “**In force.** An installed object is in force if it is on the computer; a program, if it runs or can be started.” Coverage depends on S8.2-16. No factual assumption about any real staging mechanism is made here.
- **A program is staged so it cannot start:** program startability and installed-object presence have distinct tests under S8.1-9. Whether the staged object is installed must be established; calling it inactive does not establish exemption.
- **An implementation has many preparation steps:** that alone does not imply any changed in-force requirement. Thus the supplement's expected result is justified only for a non-indivisible change in relevant effective requirements, not for every operation with multiple internal steps.
- **Success is eventually displayed:** the text uses a report, so a claim of one indivisible switch must include whatever event counts as that report. The argument does not silently replace an actual report by an earlier hidden marker.
