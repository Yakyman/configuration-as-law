### Conditional incompatibility argument and its strongest objections

1. **The earlier success keeps the properties applicable.** S8.3-1 applies after the completed D0 application, including during a later ordinary update. S8.1-14 selects D0 until another successful report. **Objection:** application temporarily suspends the properties. **Reply:** that inserts an exception absent from S8.3-1. The action is expressly assumed ordinary; it is not reclassified as breaking merely because it fails. S8.1-15: “**Breaking**—a change to what is installed or settings, made past the declaration through the power of superuser privileges, outside the built-in tools: by writing directly to files, deleting, or disabling system mechanisms.”

2. **Before the report, old requirements still govern.** S8.1-12 and S8.3-5 require x0 and y0. If x1 becomes effective first, A2 violates P2. Finishing all state changes before reporting instead leaves A3. **Objection:** editing D1 immediately makes it govern. **Reply:** S8.1-14 selects the last reported successful application, not the pending edit. Section 8.5’s exclusion of edit timing does not supply another active-declaration rule.

3. **An earlier report does not cure a partial effective change.** If D1 is reported before all its conflicting targets hold, S8.1-14 selects D1 and S8.3-5 fails at A4. Thus, for two distinct effective-change instants and only a D0-to-D1 report, reporting before, between, or after them leaves a violating state. **Objection:** the objects still have lines, and the tool wrote D1. **Reply:** P1 coverage and P4 recording are separate from P2 fulfillment. A P2 failure suffices to falsify the conjunction; no automatic P1 or P4 failure is claimed.

4. **Interruption and later restoration do not erase that state.** S8.3-1 still covers I1–I3; S8.1-14 leaves D0 in force without a later success. A restored I4 does not make earlier values equal x0/y0. **Objection:** nobody can observe the update interval. **Reply:** the text refers to actual moments and actual force, not observation. S8.1-10: “A setting is in force if it has its value.” S8.1-11: “A service is in force if it is enabled; an account, if it exists.” Pausing observers alone does not change either condition.

5. **The universal conclusion fails against an indivisible whole change.** A5 can switch all required effective state, the declaration and its success report together. D0 governs the conforming before-state and D1 the conforming after-state by S8.1-14; S8.1-12 and S8.3-5 are met on both sides, and the tool can record the change as S8.3-7 requires. No sentence requires these components to change separately. The text therefore **allows this possibility**; it removes A2–A4 and the corresponding interrupted mixed states. This is a counterproposal to inevitability, not a demonstrated working computer. An indivisible activation followed by a separate report does **not** meet the premise: A3 remains.

6. **Intermediate successful applications are another objection to inevitability.** The requested update could report a sequence D0, Dm, D1, each matching the corresponding state. S8.1-14 would select Dm after its success, so the premise that D0 governs every intermediate state would be false. Neither S8.1-13 nor S8.1-14 bans that scheduling. S8.1-13: “**Application of the declaration**—an action of the system that brings the computer into conformity with the declaration.” Each individual transition still needs the same continuous guarantees; this possibility is not proof that an implementation achieves them.

Preparation, staging and mechanism do not justify additional gaps. S8.1-9: “**In force.** An installed object is in force if it is on the computer; a program, if it runs or can be started.” A staged installed object cannot be excluded from P1 merely because its generation is inactive; coverage must be established. S8.2-16: “What is installed is recorded by one of three lines: a line of its own; the line of the package as part of which it was obtained; a line from which the system itself built or obtained it—a compiled copy, a generated list, a package installed as a dependency of a recorded package.” Conversely, several internal preparation steps need not change any required effective state. The supplement’s expected partial-state violation applies to separated changes of conflicting effective requirements, not every operation containing multiple instructions.

Section 8.5, quote: “User authority, generations and rollback, protection of the declaration itself and secrets, when an edit takes effect. The form of the declaration: it may be a list or an algorithm.” Missing design prescriptions on these subjects are not gaps. Any claimed indivisible implementation must include the actual event that qualifies as its success report; an earlier hidden marker cannot simply be substituted for a later report. No interpretation of a particular reporting mechanism is needed for these symbolic cases.

### Refutation attempts and boundary of the result

1. **Strongest objection: the line must already state its requirement.** S8.1-12 can be read as requiring each admitted line to have enough meaning to determine its required state; S8.3-5 delegates to that meaning. A primitive taking an external list can have a documented snapshot, current-list or offline policy without spelling the entire policy out each time. Under this reading, the example has not supplied a complete admitted line. The counter-reading is that S8.2-18 expressly permits the named source to count as recorded, but supplies no time rule, so the source-only line is admitted with the temporal question unanswered. S8.1-12 does not itself choose a time. These are competing readings of two identified sentences, not a choice of caching policy made here. The registered author-reading rule therefore applies: **?**.

2. **Unknown implementation semantics would be missing facts.** If L belongs to a real language whose documented semantics select a list, those semantics determine its requirements through S8.1-12. Failure to collect them is **FACT_UNKNOWN**, with the missing fact being the defined meaning of L; it is not a textual gap. No real-language fixture is asserted here. Likewise, failure to collect the remote list in a real observation would be FACT_UNKNOWN. Both remote values in B2 are stipulated, so that distinct issue does not explain the candidate temporal ambiguity. Different systems choosing different defined policies is not a gap.

3. **Several permitted outputs need not mean an undetermined requirement.** A line may permit more than one state. A specified rule allowing both retained and current lists would decide that the B2 retained list is acceptable. The disputed question is whether it is acceptable under the source-only line at all: the snapshot reading accepts it and the current-source reading rejects it. No uniqueness requirement is being added. If the source-only line itself means mere provenance with either list permitted, that is another reading that requires author resolution, not a policy silently adopted here.

4. **The external-source exceptions do not settle the offline requirement.** Section 8.4, quote: “For a line that takes a list from outside the declaration, the declaration shows which source determines the list.” Also, quote: “For a line that takes a list from outside the declaration, reproducibility is not claimed.” These defeat a demand to reconstruct the list from the declaration alone or reproduce one fixed list across machines. Neither states an offline waiver of S8.3-1/P2 or selects a time. Section 8.5 permits algorithmic declarations and excludes design mechanisms; it prevents treating the lack of one universal caching mechanism as a gap. It does not expressly answer whether an admitted source-only line may lack any temporal meaning.

5. **A cache label and P4 do not supply the missing meaning.** Accounts are settings under S8.2-13, regardless of storage. S8.2-6: “What an object is is determined by four questions asked in order; the first affirmative answer decides, and the clarifications do not change this order.” A program-record classification cannot bypass earlier questions merely because a file is called a cache. Conversely no cache behavior is assumed here. P4 (S8.3-6–8) forbids an ordinary bypass; it does not make every change obtained from a named source a bypass, since S8.2-18 expressly allows that source. Neither rule chooses between the candidate lists.

The tempting universal-impossibility chain would be: S8.2-18 names R; therefore its **current** contents must hold; S8.3-1 applies offline; P2 (S8.3-5) then requires unknown remote changes immediately. Its second step has no deciding sentence unless L already has current-source semantics. An information-impossibility conclusion would also require premises excluding prior knowledge or other communication. Those premises do not follow from the fixed definition. An explicitly defined snapshot meaning is a strong objection to universality; this argument does not propose adopting it for the disputed line.

A whole change made indivisibly is allowed here too. It does not decide which list an otherwise undefined L requires at B2. With defined snapshot semantics, an indivisible application can leave the required snapshot and remove the alleged conflict. With current-source semantics, making a local operation indivisible does not by itself supply remote information. Thus atomicity neither establishes the source-only gap nor produces a definition-wide impossibility.
