# Agreement audit: A3 sample rows 151–300

The 150 original objects were joined by stripping only the sample machine prefix. All original JSON member fields were decoded; every group member table was opened and its completeness and row count checked. The sample's malformed member encoding was not interpreted. `a3-second-evidence.tsv` maps every result to the original object and member/query evidence. Paths in its third column that start `raw/` are relative to the directory of the original object table in column two. No earlier classification, adjudication, other party result, or other task folder was read.

The question is whether the agreed decision label follows. The original reasons are not audited. In particular, identifying an executable is unnecessary to establish that an observed process is RUNTIME: every possible executable leaves that label unchanged. A declaration's current contents are not required to identify the permissible recording route. Missing actual declaration coverage would be a separate completeness check.

An executable permission bit alone is not proof of executable code. A generated-looking filename alone is not proof of derivation. ## Derived-code review and six unresolved factual cases

Two compressed updater archives: original IDs `92303a3b6a6e1ad452236f8b` and `b9490dffe916c5dcc4575874`. `A3/in/operator/gaming/actions-logs/actions-logs/gaming_store_runtime.log` names both exact archive basenames as pending downloads. Thus these are not merely guesses from a directory name. Nevertheless, no retained member listing or byte-format evidence establishes their exact contents, execution semantics or installed-package relationship. Their filesystem record gives executable permission and a prefix digest, not code interpretation. RECORD cannot be proved by skipping questions one and two.

Bytecode group `gaming-d6a1624ce14a9344ec8d659f`: the complete list contains seven .pyc files. The decoded lutris.postinst in `A3/in/raw/gaming/raw/0455-metadata-read-320.out` runs `py3compile -p lutris`; successful package setup appears in `A3/in/operator/gaming/actions-logs/actions-logs/gaming_prerequisites.log`. The package-files table verifies all seven matching source files unchanged under original package `be8e5cf13c046a178fc7e8e7` and verifies /usr/bin/py3compile unchanged. [Packaging policy](https://www.debian.org/doc/packaging-manuals/python-policy/) says bytecode “should be generated in the package’s post-install script”. The complete matching output group, compiler, sources and specific successful package setup establish the generating mechanism. There is no observed alternative origin, and S8.2-16 does not additionally demand cryptographic output-to-source proof. This group receives FOLLOWS for PROGRAM-DERIVED.

Bytecode group `server-ab60c4296b0c35885f31cca0`: the complete list contains four .pyc files. All matching sources are unchanged under package `328ea3408632a89a16aca3df`, which is netplan.io. Crucially, the saved compiler script in `A3/in/raw/server/raw/0112-metadata-read-256.out` belongs to python3-netplan, a different package (`2d8da38c92da3435c54439be`). Its `py3compile -p python3-netplan:amd64` command therefore does not establish compilation of the sampled netplan.io files. Their distinct lists are retained in `A3/in/raw/server/raw/0007-metadata-read-128.out` and `A3/in/raw/server/raw/0013-metadata-read-512.out`. No netplan.io postinst or exact runtime generation event was found in retained metadata. This concrete mismatch leaves the generating source/trigger unestablished; the group receives FACT-UNKNOWN, without demanding a cryptographic derivation proof.

Three executable files in a content-hash k3s data directory: original IDs `0343cc0e3743fdc6279f4a3e`, `9c59629a43e8b28a746de9d5`, `a1bf573f2de859142047fce6`. [Initialization documentation](https://docs.k3s.io/blog/2025/03/25/K3s-initialization) states: “At this point, K3s will extract the binaries.” The operator log `A3/in/operator/server/actions-logs/server_orchestrator.log` records download verification, installation, and startup. The ordinary extraction mechanism and installation are established. However, received-content integrity is not retained for these individual executables. The native ownership collector labels them outside native packages; that does not establish absence of packages under the broader S8.1-6 definition. If they remain as received parts of the installer-managed bundle, question one precedes the program question. Thus the exact category, and hence PROGRAM-DERIVED, depends on an unknown first-question fact. This is not a general demand for cryptographic derivation proof or a choice between wording readings on complete facts.
