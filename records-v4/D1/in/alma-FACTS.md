### alma

The complete collector directory is `D1/in/raw/alma/`. To resolve a row in `part-alma.tsv`, remove its leading `alma-` from `id` and match `id` in `raw/alma/objects.tsv`. Its columns are `id`, `machine`, `level`, `kind`, `name`, `members`, `evidence`. The transformation preserves every source row, source order, machine, name, members and evidence; only the required prefix, part and combined level/kind are added. All paths inside source `members` and `evidence` are relative to `raw/alma/`.

- Package reasons: `raw/alma/objects.tsv`, rows with `kind=package`; the JSON in `members` gives `manager` and `reason` (`explicit`, `dependency`, `unknown`), with native reason/provenance fields where collected. `evidence` links exact query outputs. RPM records specifically link `D1/in/raw/alma/raw/0015-packages-rpm.out`, `D1/in/raw/alma/raw/0016-package-reasons-dnf.out`, `D1/in/raw/alma/raw/0017-metadata-read-0.out` and `D1/in/raw/alma/raw/0018-package-selected-groups-dnf.out`. Unknown stays unknown.
- Packaged-file integrity: (not published: over 20 MB), columns `package`, `path`, `integrity`, `evidence`, `rule`. Join `package` to the unprefixed object ID. `integrity` is `unchanged`, `changed`, `missing`, or `unknown`; the known share includes the first three. It describes collected package-file records; unsupported manifests are not invented. Package directories are omitted by the collector itself. File signatures from filesystem traversal are not installation-integrity facts.
- Stored group membership: every `L2:stored-ownership-unresolved` row has JSON `members.file`, `members.count`, `members.complete`. The exact file is `raw/alma/members/<unprefixed-id>.tsv`; columns `path`, `type`, `mode`, `owner`, `size`, `mtime`, `executable`, `signature`, `persistence`. These contain every immediate child supplied by the collector. The group's own `name` is its directory path. Other structured group/package/service rows retain their complete collector JSON in `objects.tsv:members`; no membership is inferred beyond the collector's representation.
- Persistence: (not published: over 20 MB) contains the filesystem JSON records keyed by `path`, including `persistence`, `filesystem` and `readonly`. For stored groups, match `objects.tsv:name` to `path` for the group directory itself; each listed child has its own `persistence` in the member TSV. For `code-ownership-unresolved`, the same metadata is directly in `objects.tsv:members`; for `image` and `image-container-store`, in `members.metadata`. `persistent`, `runtime` and `unknown` remain distinct; these describe mounted filesystem properties, not the disposable machine's retention.

`raw/alma/coverage.tsv` gives `query`, `exit_status`, `duration`, `rows`, `bytes`, `stdout`, `stderr`, `status`, `object_rows`, linking every failed query to its exact raw command/output/error files. `raw/alma/metadata.json` records complete filesystem traversal but incomplete package ownership, and all collector gaps. Unsupported ownership remains unresolved. All ordinary-action outputs and exit statuses are in `control/alma/actions-logs/` and `control/alma/actions-status.tsv`; the disposable machine was destroyed successfully.

For `L1:group` rows, `D1/in/raw/alma/objects.tsv` JSON `members.record` retains the entire captured `/etc/group` record (name, password placeholder, numeric group id, comma-separated named members); `evidence` points to `D1/in/raw/alma/raw/0003-metadata-read-0.out`. This is the source group record, not a synthesized list of all effective account memberships. The captured `L1:account` records preserve primary numeric group ids separately.

Collector invocation deviation: the unchanged collect.sh wrapper was invoked with explicit bash rather than executed directly through its committed /bin/sh shebang. This was an operator wrapper choice with no documented requirement or observed compatibility failure; no rerun was performed.
