The mandatory boundary comes from [codeboundary.py](../build/codeboundary.py), [session.c](../build/session.c), [codeverify.py](../build/codeverify.py) and [guard.py](../build/guard.py):

- The ordinary login shell is a static launcher accepting one tab-separated `run` request with a declared entry key, or `broker` with a named frontend and value arguments. It performs no shell expansion, evaluation, pipelines, redirection, functions or aliases. General interpreters, compiler/build/debugger entrypoints and dynamic loaders have no ordinary launch entry. Recorded scripts have explicit `entrypoints` naming script and interpreter; both hashes are checked. Interpreter options and environment are fixed, stdin is `/dev/null`, extra arguments refuse, and inherited descriptors close before exec. Output uses write-only pipes.
- AppArmor profiles come from the declaration. Execution is limited to the selected recorded binary; executable mapping requires an immutable declared ELF path, independently of download method, name, directory or mount. Admission rejects foreign managed ELF, executable stacks and writable/executable load segments. New mounts/namespaces cannot create an execution route.
- General recorded programs/scripts run in an immutable input root containing only declared immutable readable files, recorded aliases and a null device. Fixed privileged setup enters this root, changes cwd, permanently drops supplementary groups and all UID/GID values to 1000, then installs Landlock and no_new_privs/seccomp. The view has no user home, temporary tree, procfs, shared memory, inherited input FD or network/IPC input. Filename/stat/O_PATH/handle-based instruction inputs are absent too. Verification checks exact snapshot membership, ownership, modes and contents.
- Seccomp rejects executable anonymous memory, W+X mappings, executable mprotect/pkey_mprotect/shmat, memfd, process-memory injection, alternate ABIs, namespace/mount operations and low-level kernel interfaces. Sealed code cannot create/connect sockets; SysV IPC, message queues and keyrings refuse. Bind/listen refuses in all workload modes. AppArmor prevents helper launches and unrecorded libraries. Descendants inherit confinement.
- Fixed data tools are `cat`, `cp`, `mkdir`, `curl`, `w3m`, `red` and `dd`. They retain the native execution/mapping/syscall boundary while reading user data. `dd` is a literal document writer: exactly one home pathname, forced output/status options and verbatim stdin. The real headless editor uses GNU ed restricted mode through `/usr/bin/red`, fixed `--restricted --script` options and one home basename; line replacement and saving work, while shell commands and command-output reads refuse. `w3m` uses a recorded fixed configuration and dump mode, with no webpage JavaScript or caller configuration. Future declared programs default to sealed mode, never automatically to data mode.
- Managed services start a fixed setup binary as root in their manager-owned cgroup and preinstalled AppArmor profile, then execute the declared workload after the same permanent identity drop and isolation. Manager no_new_privs is deferred until that fixed setup completes; the launcher then locks it for both child and output relay and clears all inheritable/permitted/effective/ambient capability sets. The explicit `code-boundary` requirement records this transformation; verification checks the exact generated override and active MainPID credentials, zero capabilities, no_new_privs and enforcing profile. The workload is not a root process. Ordinary callers cannot enter the manager-only setup route.
- On code or job-set change, application stops managed sockets, then timers, then services and keeps them stopped through policy/input-root activation. Code removal/change revokes every living generated workload domain, including descendants, before replacement; a second revocation precedes candidate job restart. Removed entry keys, profiles and input-root names disappear; copies in writable data trees remain nonstartable. Verification compares generated policy source with the kernel's loaded binary policy objects and exact active domain set, not merely profile names.

The setup binary admits only the declared ordinary UID or a manager invocation, and drops privilege before data tools or broker sudo. It exposes no general root command. External operator root can deliberately change these mechanisms, as S2.1-7/8 allow. Setup and workload bytes themselves belong to factory declaration lines.

## Declaration and defaults

The selected declaration is `/var/lib/stand/current`, a directory of files: `machine.jsonl` is one JSON object per line, and `base-files.json` is its checked base manifest. [example/](../example) contains the complete factory declaration exported from the final image; it is not an abbreviated template. A generation is identified by SHA-256 over sorted file names and exact bytes. Each installing line has `id`, `type`, `version`, `source`, and exact file hashes, modes, uid/gid and symlink targets. Managed payload bytes are inline base64; the loader checks their checksum before changing live state. File manifests must be in that same directory. Conflicting contributions to the same file are rejected. Package/base contents come from the frozen image. A trusted build-time catalog can replace the complete exact base state; other factory changes refuse.

For a small complete *additional* line, [build/dev-inputs.py](../build/dev-inputs.py) generates the native development artifact with every payload byte; the complete declared machine is the factory directory plus that line. A firewall line is:

```json
{"id":"dev-rule","type":"rule","managed":true,"expression":"tcp dport 17777 drop"}
```

Its fixed defaults are nftables family `inet`, table `stand`, chain `input`, filter type, input hook, priority 0 and accept policy; the line ID is its nft comment. The narrow grammar accepts TCP/UDP destination-port accept/drop rules. Other existing firewall tables are neither managed nor proven absent by subsequent applications.

## Application, comparison and removal

`stand-apply DIR` takes one nonblocking application lock, then delegates inactive preparation, validation, activation and per-line readback to a separate process group. The supervisor cancels a silent worker after 3300 seconds by default, leaving a 300-second recovery allowance within the one-hour interval. A root-only test setting shortens the total interval to 60 seconds and cancellation to eight seconds. Every mutation phase has an explicit fault-injection checkpoint. A systemd timer independently detects abandoned/overdue supervisors using process start identity and kills their worker group before acquiring the lock and recovering. Recovery that itself stalls or encounters an unhandled device effect remains a limitation; a deadline value alone is not a proof of complete restoration by that deadline.

The journal records previous and candidate generation identities. Recovery takes the durable `last-success.json` report as authoritative and reconciles from the possibly partial candidate to the reported generation. Thus candidate-only files, accounts, units and rules are inverse-operation inputs even if the selected link still points to the old generation. Missing candidate units/files are tolerated; actual stop, unlink and identity-deletion failures raise. The union of target/candidate activation edges is stopped before revocation, so incomplete activation cannot leave an old target service racing restoration. An unresolved journal must be recovered before a new transaction can overwrite it. Runtime state is verified before the journal clears and admission reopens.

Success follows worker termination and complete candidate readback, selector/file/directory flushes, realization sync and an atomic durable local report. Stdout forwards that report. A crash between selector and report recovers the preceding report; a crash after the report recovers the reported candidate, even if pending cleanup did not finish. No later stdout error produces a contradictory failed report or restores an older generation. This report medium is a design choice, not a new hypothesis rule.

Boot uses the same reconciliation. `/run/stand-ready` is absent after power loss and written only after replay readback. A requisite PAM account test refuses both ordinary and external operator login sessions until that marker exists; the ordinary launcher checks it independently. Getty, logind and user-session services require replay. SSH may listen beforehand because the listening endpoint itself is recorded and verified; no early login session is authorized by that fact. The host wrapper additionally waits for replay.

`stand-verify` prints one row per required line using file, account, service-manager, SSH, firewall, mount, listener and network readback. `stand-compare --snapshot FILE` saves those actual values for the operator; ordinary callers use `--snapshot -`. Comparison includes installed file hashes/permissions, enabled-state/unit hashes, account tuple and effective rule text. Independent rebuilt installations use the same explicit package and laboratory key inputs; private laboratory keys stay outside published records.

`stand-inventory` is a distinct census over files throughout mounted ordinary trees (including home/container trees), system/global/available user managers, accounts/groups/effective privilege observations, configured key paths, rules/listeners, saved profiles, process credentials and executable mappings, mounts and accessible boot variables. Coverage requires a matching line stating required state. Unknown files, dormant signatures, unsupported managers/namespaces and unreadable external firmware state remain explicit unknowns; output `complete:false`, `p1:"?"` does not certify P1. Root planting verifies visibility of all tested kinds, not semantic completeness. Readback and census together provide the available P2/P1 evidence without concealing missing observations.

Removal first withdraws socket/timer/service activation, stops whole service cgroups and revokes all confined workload holders, then replaces exact file/input-root/profile membership. Only remaining explicit contributions authorize files, unit/account identities and effective rules. Exact duplicate claims are accepted; conflicting claims refuse. A rule table is atomically regenerated from remaining rule lines. Required active sockets finish starting before timers, then services. This respects the admitted activation graph regardless of declaration line order; systemctl submits a separate native StartUnit request per argument. Socket nodes use `RemoveOnStop=yes`; unsupported dependencies, automatic restart and other activation directives refuse. External superuser changes remain breaking, not ordinary activation paths. Declared OCI containers additionally use their own immutable image root. Container removal revokes the common launch/profile authority before retaining any image archive as inert bytes; there is no separately mutable container daemon.
