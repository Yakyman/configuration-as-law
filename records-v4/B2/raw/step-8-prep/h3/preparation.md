## Source-based launch expectation after native prerequisite installation

The selected candidate remains committed, and its single second-party attempt is mandatory. Successfully installing native packages does not establish that the ordinary shell can execute them. The frozen recipe has two relevant boundaries:

1. `B2/build/codeboundary.py:22-25` constructs native policy inputs only from the machine declaration's `base`, `program` and `code` manifests. Its `generate` function permits executable mappings only for immutable ELF files in that set. `B2/build/shell_boundary.py:159` onward generates the ordinary `stand-shell` profile's inherited execution rules from that same set; it has no wildcard executable permission. `B2/build/codeboundary.py:180-202` writes and loads that generated policy through the declaration transaction. Native `/usr/bin/dpkg --install` is not that transaction and has no automatic manifest-registration/policy-refresh hook in this recipe. Consequently the added `/usr/bin/tmux`, `/usr/bin/jq`, and other previously absent native executables and libraries are expected to remain outside ordinary launch/mapping admission. The prerequisite installation can itself succeed while the ordinary launcher subsequently fails. This is a source-derived prediction, not an observed denial.
2. Independently, `B2/build/bc3_filesystem.py:617` mounts the mediated writable filesystem with `noexec=True`, and `B2/build/noexec.py:3-12` requires `noexec` on writable trees including `/home`. The committed LinuxGSM invocation uses its default `serverfiles` under the ordinary user's working directory, so the extracted native game executable is on the noexec filesystem. Merely recording its writes does not remove that mount restriction. Directly starting the game there is expected to fail even if prerequisite execution succeeds.

The existing ordinary `stand-import install` interface (`B2/build/import_channels.py:16-33`) can admit one checksum-fixed ELF or explicitly interpreted file by installing it at `/opt/stand/pkgs/ID/bin/program`; `stand-pkg` can likewise apply a supported package artifact. These are distinct explicit declaration applications. They neither automatically import native dpkg package registrations and all their runtime libraries nor automatically relocate a launcher's downloaded game tree and selected executable. The committed candidate does not insert such manual replacements, remount writable trees, execute the game as root, or bypass native launch admission. No general impossibility claim is made: a failure of this committed launcher on this prototype still requires the second party's output and the separate review specified by step 8.

## Action receipts and game-start readback

Both scripts now emit paired `ACTION_BEGIN` / `ACTION_DONE` phase receipts and an `ACTION_FAILED` receipt on a failing command. A missing DONE is not success. Before each game stop, the ordinary process query scans `/proc` and requires an actual live, non-zombie `etded` process whose executable is the exact downloaded `serverfiles/etded` and whose entire argument vector equals the pinned LinuxGSM default start parameters. It saves PID, executable, comm, argv, state, starttime, and unreadable-process diagnostics. A successful `wetserver start` exit or details page alone does not meet this criterion.

After each orderly stop flushes the game's logs, the query requires `------ Server Initialization ------` in `serverfiles/etmain/etconsole.log`. The pinned game configuration enables `logfile 1`; official game source `src/server/sv_init.c` emits that marker, and `src/qcommon/common.c` opens `etconsole.log` with `FS_FOpenFileWrite`. Source references and hashes at commit `40342a9e3690cb5b627a433d4d5cbf30e3c57698` are included in the source manifest solely to explain the query; the actual chosen game archive is unchanged. Failure of the marker or process proof is retained as an uncompleted action, never inferred away from command exit status. The configuration checksum remains before the first start. The script prints the exact launcher file SHA-256 before self-update and again after it, in addition to the normalized source-identity check.
