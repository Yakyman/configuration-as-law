# Filesystem component internal engineering review

Recorded 2026-11-23 UTC. Source review only; no machine probe and no external acceptance. Reviewed `B2/build/bc3_filesystem.py` SHA-256 `3476b150e122237d3233fb91703453586e56b67c3a92c89589e38b9fadba6453`. Later edits require their own source identity.

## Findings

1. Integration requirement: existing primary declaration claims must not retain superseded exact writable-file hashes or account tuples. The filesystem's separate primary declaration does not erase contradictory rows in the original declaration. Every-line verification must cover both; fixture marker success cannot substitute for it. The image installer was not available at this review point, so reconciliation remains unverified.
2. Scope limit: every mediated mount has `noexec`. All fifteen fixed saved-input ways use an explicit admitted interpreter/consumer and can still work, but direct native/shebang execution from these namespaces is unavailable. No general all-program execution closure follows. The ordinary personal script must remain in the protected managed package namespace as the supplied ordinary-work command specifies.
3. Description correction: open handles pin inode identities, not immutable historical versions. `read()` resolves the inode in current state; an in-place write updates that inode for every handle, preserving ordinary shared-file semantics. An unlinked inode with a live handle remains in the current objects map; rename-over retains the displaced inode while handled. State maps and actual reads therefore agree under serialized callbacks. The broader prospective pinned-version design in ARGUMENT-5 is not an implemented feature claim.
4. Audit limitations: read completion and executed markers are not recorded by the filesystem. Audit reports successful changed paths/hash values. Prepublication ordering rests on source logic plus mounted operation evidence; post-state file coverage alone is not temporal proof. Ordinary fixture setup is already automatically recorded, so the case must be described as recording at saving, not as a previously unrecorded read being denied.
5. Failure/restart limits: after switching `current`, any exception puts the daemon in failed state; subsequent callbacks fail. A restart validates blobs and active paths, then retires unlinked objects because no userspace handles survive. The service/mount recovery path must actually enforce that assumption; surviving kernel mount references across daemon failure are not validated here. A failure before pointer switching may leave inaccessible staged generations/blobs; startup selection of a predecessor from directory names can include abandoned future staging. That does not change the selected current declaration, but cleanup/provenance should not call such a predecessor an applied generation without checking.
6. Required positive-case evidence: SAVED-SCRIPT and PYTHON-IMPORT use compound write-then-run commands. The shell's final exit status and marker can hide failure of the preceding write; successful write audit evidence or absence of write-error diagnostics is needed. PICKLE-CODE propagates its write failure within the same Python command. Account validation should compare the full original expected tuple as well as actual state against declaration rows.

## Mechanism assessment

No obvious ordinary read/write publication race appears within this single-thread callback model: the service creates durable private blobs, writes declaration and success files, changes their shared current pointer, updates in-memory state, then returns the original mutation callback. Subsequent callbacks cannot run between those steps. The transaction does not invoke the carried global freezer, avoiding a filesystem-request/freezer dependency cycle. Initial seed copying occurs before service admission. These are bounded source findings, not proof of all P1/P2/P4 transitions or whole-system coverage.

Remaining substantive objections are intentionally retained in ARGUMENT-5 and QUESTIONS-5: the interpretation of private staging versus primary description; previously read bytes and old stored versions; ordinary work on unsupported operations; and the complete designation/coverage of multiple declaration files. No definition-only impossibility conclusion follows.
