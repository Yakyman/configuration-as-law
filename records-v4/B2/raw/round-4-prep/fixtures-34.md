## Internal source review of complete replay, initial revision

Requested as a separate bounded preparation check, 2026-11-23 UTC. This is not
the independent execution/review required by the supplement. Findings refer to
the first inspected revision of `B2/build/bc4_bundle.py` and its corresponding
`bc3_filesystem.py` additions; the integrator may resolve them before freezing.
No runtime probes were used.

1. **Missing final realized-state check.** `apply` checked selected declaration
   bytes after replacing five filesystem descriptions, but `stand-apply` had
   checked machine requirements before that replacement. A contradictory `/etc`
   filesystem could therefore invalidate an account, file or service requirement
   and still receive complete success. Require full machine and filesystem
   readback after the final restore and before the receipt, followed by another
   exact declaration identity check. Effective manager state also needs to agree
   with restored units and drop-ins, rather than relying solely on their bytes.
2. **Invalid future inode allocation.** The original filesystem validator did
   not require `next_inode` to exceed all existing inode IDs or require the root
   inode to be a directory. A later allocation can overwrite an existing inode
   if the imported counter is too small.
3. **Omitted account semantics.** The validator checked `account_rows` only if
   present, while exact replay bypassed normal regeneration. Require the field
   and its exact prospective database-derived value for the account filesystem.
4. **Export consistency.** Export rechecked each filesystem immediately after
   reading its blobs, but never rechecked earlier files after reading later
   files. A final all-eight-file consistency check is needed before publishing
   the bundle; otherwise it can combine states from different moments.
5. **Complete receipt durability.** Direct `write_bytes` on the success receipt
   was neither an atomic replacement nor explicitly durable. Use atomic durable
   publication with directory synchronization before printing complete success.
6. **Socket service survival.** Reply `sendall` was outside the connection's
   error handler. A disconnected or timed-out client could terminate the single
   application thread. Handle the reply error and return to accepting clients.
7. **Generation rewind limit.** Exact replay admits older generation numbers,
   while daemon initialization identifies the prior generation by a smaller
   number. After a rewind, it can ignore the true predecessor, leaving retention
   metadata inconsistent with the intended current-plus-previous policy. This
   is a recovery/cleanup limit to resolve or state explicitly; no case failure
   is inferred.
