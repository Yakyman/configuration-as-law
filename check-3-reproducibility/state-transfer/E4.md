## Question and method

O8 asks whether and how derivatives should travel separately from the declaration. §5.3 does not promise that unrecorded objects appear on another computer. We tested a program/service declaration first, then a separate state archive, then narrowly targeted repairs after recorded failures. The premeasurement protocol and input hashes preserve the scope.

Two fresh overlays of B's original Debian 12 cloud image were independently bootstrapped, without B's prepared controller image. Each ran on `<HOST>` with **4 GiB RAM / 2 vCPU**, under user systemd. They ran sequentially. No experiments or system changes ran outside these VMs; local writes are the E4 records. Launch, source, target.

The source's [declaration](raw-E4/src/declaration.json) was copied to the clean target and applied using the same [recipe](raw-E4/src/apply.sh). Both had SHA-256 `257920861d4296e2574173bb2911515de35aab62e942ef43e572f42d5d9457e2`. This is a limited instrument recipe, not a full declaration/enforcement implementation. ## What these data support or rule out

- **Separate state export/import is feasible** for these same-version programs. Declaration-only application did not restore their unrecorded state; the verified archive restored several useful behaviors. This supports offering a separate transfer mechanism, without deciding whether it should be mandatory.
- **Unconditional unchanged copying is insufficient for the tested selection.** The MAC-bound profile and host-encrypted credential failed despite verified bytes. Copying a directory named for a service also need not include all its state: PostgreSQL's external tablespace was a deliberate dependency-omission test, not evidence that a complete backup cannot work.
- **Selective transfer with application-aware repair is supported:** preserve compatible profile/database state, rebind hardware/path references, and decrypt/re-encrypt a credential when the source context is available. These are demonstrated options, not proposed obligations for the hypothesis.
- **Identity preservation versus fresh identity remains a choice.** Copying the SSH key preserved client trust; generating a new key changed it. The data establish that tradeoff, not which identity the author should choose. Changing the whole target's machine-id was unnecessary for the successful re-encryption route.

## Limitations and retained defects

One source/target pair, same Debian release, software versions, CPU architecture and physical KVM host. Identifiers differed; this was not physical-hardware diversity or §9.4 reproducibility testing. The recipe did not implement P4 or automatically discover derivative ownership. Fixture commands supplied database rows and browser values; storage files were program-produced, but their classification as derivatives versus personal data remains **O1/O2 `?`**.

Ethernet tests measured only the isolated gateway, not Wi-Fi/Bluetooth, DHCP/DNS portability or live TCP sessions. Browser tests covered three persistent stores, not passwords, desktop keyrings, extensions, crashes or all browser-created files; a separate 40-byte Chromium crash-settings file remained outside the transferred profile. No TPM device, TPM-sealed credential, security token, cross-version database migration, UID remapping, concurrent writer or crash-consistent backup was tested. Permissions/numeric ownership were preserved; ACLs/xattrs were not measured. Source identities and synthetic values are retained in logs; private keys and database/profile bundles are not retained.

Stand defects were logged and corrected: the first upload lost commands to nested SSH stdin; the transient sshd needed recreation after stop; disabling PAM rejected the cloud image's locked root account; and the first credential matrix stopped when a mismatched key file was removed. These are not transfer/hypothesis failures. Exact failed and corrected commands remain in `raw-E4/*.json`; [SSH diagnosis](raw-E4/source-ssh-auth-diagnosis-fix.json), [partial matrix](raw-E4/target-credential-matrix.json), [completed matrix](raw-E4/target-credential-matrix-complete.json).

Both VMs are stopped; E4's server directory, disposable disks, archives and generated keys were deleted after evidence export. No E4 QEMU remained. Cleanup receipt.
