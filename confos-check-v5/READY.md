# Freeze for complete run 3: release 0.70

2026-11-27 UTC. The portable cases, semantic declarations, payload sources and
checking programs were published at records commit `1619b5bc`. Since then the adapter
was bound to the builder's interface (BINDING.md), regenerated for releases 0.65, 0.66,
0.67, 0.68 and now 0.70 — the release named for run 3 — and repaired after trials. CORRECTIONS.md
lists every change since that commit, with the trial that found it. The cases and the
semantic declarations are the same set that ran in complete run 1 on 0.67 (RUN-1.md)
and complete run 2 on 0.68 (RUN-2.md);
only the binding to the system changed with the release. SHA256SUMS freezes the set;
PUBLICATION.txt lists the files to be published before complete run 3.
Nothing has been published by the case party.

This is **not a run**. Trials report nothing about the system. Complete run 3 starts
only after this set is published, on release 0.70, from a clean installation, every case
and every variant; nothing in this set changes between the publication and the end of
the run.

## Publication set

- README.md — entry point, self-test command, the binding in one paragraph.
- STATEMENT-LABELS.json — the 34 labels from records-confos/TABLE.md, with
  source checksum; catalogue validation needs no external file.
- PROGRAMS.md — base admission decisions, written first for the builder.
- PORT.md and port.json — 153 source case/step IDs, 19 search cases individually,
  with all generated check families retained.
- CASES.md, casedefs.py, plans.json — 86 portable cases, 159 executions with their
  variants, all 34 TABLE.md statement labels, including the eight previously untested.
- declarations/ — semantic test, opening, account, external-source, shared-owner,
  radio and update inputs, with payloads.lock.json.
- payloads/ — small C programs, recipes of the case packages, recorded/unrecorded
  shell inputs and harmless values. Source code under the MIT licence; see
  LICENSE-CODE at the top of the repository.
- adapter.py, adapter_native.py, adapter_disk.py — the only code that knows how the
  system is built, booted, reached and read (stand plans; native lifecycle, transport,
  queries, inventory; confpkg reader and external disk reader).
- core.py, engine.py, cli.py; run, derive, inventory, compare — derivation,
  comparison, per-check/per-case evidence, request extraction, the suite of variants.
- bindings/ — release-0.70.json and commands-0.70.json, generated by
  tools/make_bindings.py and tools/make_commands.py from the documents of release 0.70.
- BINDING.md, CORRECTIONS.md, FORMATS.md, ASSUMPTIONS.md, QUESTIONS.md,
  local.env.example — binding, corrections, schemas, assumptions, open readings.
- selftest/ (excluding LAST.txt), fixtures/, tools/, SELFTEST.md — fixture tests and
  generators; SELFTEST.md records the self-test of exactly the published files.
- SHA256SUMS, PUBLICATION.txt and this READY.md.

Excluded: working correspondence, trial reports, local.env, STATE.md, TASK.md,
working/, private evidence, machine-specific paths, credentials, temporary work and
caches.

## Complete run 3 (after the publication)

1. Record the published commit, the SHA-256 of SHA256SUMS and the release identity
   (tag 0.70 of the builder's tree; update states: tags 0.70.1 and 0.70.2).
2. The clean package store and bootstrap root are built from the source of tag 0.70 by
   PROCEDURE 1–5, and a second independent store for the cases that compare two clean
   builds; the packages the update states change are built by the case party from the
   recipes of their own trees (the derivation input of OW-2 and OW-3); the native section
   of local.env names them, the copies of the three trees and the source archive.
3. Run every case and variant with `./run --native local.env --all --out DIR` inside
   confos.slice; write RUN-3.md and RUN-3-STATEMENTS.md, and an entry in REQUESTS.md for
   every fail and undecided row and every unobserved row whose reason is not the same as in
   run 2 (RUN-3.md says which unobserved rows are the same as in run 2 and which are new).

Hardware connection and pairing remain distinct required actions later on the laptop;
a virtual machine row never substitutes for them.
