# C1 — Attack on “Configuration as Law”, version 1 — FC1 revision

2026-11-19; correction round FC1. **Outcome: 0 for the written definitions.** A person-written executable editor configuration alone satisfies two explicit classes with different lifecycle consequences. This is a desk review of documented real object types, not an executed census or prototype test. No result is claimed for the test run’s Checks 1–5. Definitions and failure conditions are unchanged: verbatim paper extract, paper hash.

The table ranks classification failures first, followed by the conditional archive case and remaining scope, lifecycle and applicability attacks. Case IDs retain the original row numbers for review traceability. **Recorded** means an explicit declaration entry is stipulated; being installed, package-owned, or “important” does not make an object recorded. Otherwise the object is unrecorded, its named host programs are recorded, and no bypass permission is assumed. **Derivative(X)** names the program satisfying the paper’s creator-and-purpose condition; uncertainty about that conjunction is marked **hole**, not silently resolved by directory location or consumer identity. **Data** uses the paper’s human-creation definition. Composite objects are identified explicitly.

**0** = a classification the written definitions cannot decide, dual classes with different consequences, or a proved requirement contradiction (§9.1–§9.2); no proof against every conceivable repair is required. **1** = this particular attack is answered by the existing text, not a global pass; **?** = insufficient evidence for the specified claim or an unresolved law/lifecycle/scope question without a demonstrated classification failure or contradiction. Classification and law/lifecycle outcomes are reported separately where they differ. An undecided classification stays a hole with **0**; possible new ownership or decomposition rules cannot rescue it. These are desk adjudications of documented cases, not an executed two-machine census. The explicit interpreter rule in §9.3 remains **?** for law. P/O mappings identify the stressed properties and relevant open problems, including where an attack goes beyond the named problem. ## Genuine holes and the exact sentences they break

1. **H1 — Personal executable settings have two incompatible classifications (rows 01,09).** The paper says **“Code executed within a program is its derivative.”** (§5.1, L133), and **“Data—what a person has created: photographs, documents, databases, and their own settings files, such as a text editor configuration.”** (L134). Its consequence is **“If the program is absent from the current generation, its derivative is moved to an archive.”** (P6, L145). A person-written `init.el` satisfies both definitions; P6 applies through one and not through the other. O2 explicitly admits the problem without resolving it. This directly meets the written dual-class/different-consequences criterion. No firmware scope, network failure or prototype assumption is needed.

2. **H2 — Conditional hole for a locally retained ownerless archive (row 02).** **“Everything that is on the computer and is not recorded in the declaration is either a derivative of a recorded program or the person's data.”** (P3, L142) and **“Whether to keep the archive indefinitely or delete it is a setting recorded in the declaration.”** (P6, L145) leave this case undecided: stipulate that the unrecorded automatic cache archive stays **on this computer**, remove its sole owner from the current and every saved generation, and retain the archive indefinitely. No current or saved declaration supplies the recorded owner. The paper supplies no replacement-owner or historical-owner rule. **Classification 0 conditional on that local archive; lifecycle ?.** P6 does not require local storage; an archive wholly off this computer does not demonstrate this P3 conflict. Check 4's sequence (L237) does not determine location, and “archived” versus “active” (L238) is a lifecycle distinction, not a location statement. This is not a universal P3/P6 contradiction.

3. **H3 — O9 execution-scope hole, not a demonstrated contradiction (row 03).** **“Everything that runs on the computer is recorded in the declaration.”** (P1, L140) must be read alongside **“Running components—users and the rules under which they operate, programs, drivers, and services.”** (§5.1, L132), **“Code executed within a program is its derivative.”** (L133), and **“Under P3, extensions within programs are derivatives and do not count as bypasses”** (§9.3, L226). The text forces the extension's derivative classification, but does not force a broad reading that makes all internal code a separately recorded running component. O9 leaves scope open. Thus **classification 1 for this extension; scope ?, law ?**, with the extension exemption unchanged. The unresolved classifications of distinct VM, module and helper objects in other rows are assessed separately; they do not prove a contradiction for the worked extension case.

4. **H4 — Known creator/consumer and aggregate objects remain unclassified (rows 04,06,07,10,11,13–18,33,36).** The derivative definition requires **“an object that a described program has created itself because the object is needed for the program's operation”** (L133); data include **“what a person has created: photographs, documents, databases, and their own settings files, such as a text editor configuration”** (L134). Given the known provenance and contents in the cited cases, §5 does not decide initial owner, aggregate unit, launch boundary, or mixed-history status. O1/O2/O5 acknowledge rather than decide these gaps. §9.1 explicitly says **“an object that the definitions cannot classify (Check 1)”** yields 0; §9.2 includes disagreement that **“the text of the definitions does not resolve”**. Therefore these classification outcomes are **0**, even without proving that every newly invented repair is impossible. No decomposition, suite-as-program, output-as-need or ownership-transfer rule has been added. For row 18 this applies to the installer-created branch; for row 36 to the rewritten branch.

Other claims retain **?** where the relevant evidence or proof is missing, or where the unresolved question is law/lifecycle/scope rather than a demonstrated object-classification failure. The strongest physical example is row 08: the exact Generation promise is **“Generation—a version of the system resulting from a new application of the declaration; it is possible to return to saved generations.”** (§5.1, L135). On the documented chip, a raised fused minimum can make an older image unbootable on the same hardware. But a conforming system could refuse that transition while retaining the older generation. Therefore this is a concrete applicability/transition constraint, not a universal impossibility result. Creator/consumer keys and mixed databases instead have classification **0**: their known cases are not decided by the written definitions; hypothetical new criteria cannot lower that outcome to ?. Their runtime lifecycle outcomes remain **?**.

H1 alone fixes this paper-review outcome at **0**, with additional classification failures in H4. H2 is conditional on local archive storage; H3 no longer supplies an independent 0. TPM nonexportability, licence expiry, cloud outages, cache eviction, unknown migrations and ordinary system defaults were not promoted into universal impossibility proofs.
